사용자 관점에서 달라지는 결과는 다음과 같다.

1. 짧은 영상 여러 개를 이어붙여 반복 재생해도 이전 전환의 늦은 정리 작업이 새 영상 재생을 끊지 않는다.
2. 드로잉 저장이나 파일 확인 응답이 사라져도 앱이 무음으로 영원히 멈추지 않고, 건너뛰기·중단 안내·로그 중 하나로 원인이 보인다.
3. 전환 제한 시간으로 중단된 뒤에는 스페이스를 한 번만 눌러 다음 항목부터 다시 재생할 수 있다.
4. mpv가 실제로 전진했는지는 화면 보간값이 아니라 엔진에서 마지막으로 실측한 시각으로 판정한다.
5. 드로잉 마지막 획을 회수하지 못한 자동 전환은 저장 성공처럼 넘어가지 않는다. 현재 영상과 최신 획을 그대로 보존하고 이어붙이기를 한 번만 중단해 알린다.
6. 공유드라이브 파일 확인이 멈춰도 시간 초과된 확인 작업이 뒤에 남아 다른 파일 작업까지 막지 않는다.

## 배경 및 원인

실사용 로그에서 이어붙이기가 3~4회차에 멈추는 현상이 반복 확인됐다. 원인은 하나가 아니라 다음 경로가 겹친 결과였다.

- 렌더러 경고가 파일에 남지 않아 전환 실패 원인이 보이지 않았다.
- 드로잉 persistence IPC에 데드라인이 없어 응답 유실 시 전환 큐 전체가 무한 대기할 수 있었다.
- 일시적인 저장 게이트 실패도 이어붙이기 세션 전체 중단으로 승격되는 회귀가 있었다.
- `ended` 이후 비동기 전환의 예외가 격리되지 않았고 `file:exists`도 무기한 대기할 수 있었다.
- 멈춘 뒤 스페이스 첫 입력은 세션 정지만 하고 재생하지 않아 두 번 눌러야 했다.
- mpv 전진 판정이 보간 시각을 사용해 실제 엔진이 멈춰도 전진한 것으로 오판할 수 있었다.

계획서의 작업 1~6을 순서대로 적용한 뒤, 부록 A-1을 사양 그대로 3초 영상 8개로 실행했을 때 추가 경합이 실기에서 발견됐다. 이전 영상의 긴 로드 꼬리가 다음 전환 뒤늦게 살아나 새 세션의 상태를 정리하거나 같은 `ended` 요청을 중복 처리할 수 있었다. 사용자의 추가 범위 승인을 받은 뒤, 전환을 최신 사용자 의도 기준의 단일 비행으로 직렬화하는 보완 작업을 수행했다.

PR 리뷰에서는 작업 2·3의 결합 경로에 P1 데이터 유실 위험이 추가로 지적됐다. `beforeVideoChange()`가 입력을 차단한 뒤 도착한 마지막 획은 정상적으로 거절되지만, 그 획을 회수할 최종 export가 타임아웃이어도 기존 구현은 성공으로 간주했다. 이후 취소 복구가 오래된 저장소를 최신 오버레이에 다시 수화하면 화면의 마지막 획까지 사라질 수 있었다. 실제 컨트롤러·저장소 하네스로 이 연결을 재현해 보고한 뒤 사용자의 추가 승인을 받아, 자동 우회를 폐기하고 최신 오버레이를 보존하는 실패 닫힘 정책으로 교정했다.

후속 리뷰는 백그라운드 `resync-required`의 export 타임아웃이 같은 공용 실패 helper를 거쳐 `persistenceBlocked=true`로 영구 고정되는 두 번째 P1을 찾았다. 계획서 작업 2의 완료 기준인 “어떤 경로에서도 타임아웃이 차단 래치를 만들지 않는다”를 다시 전수 추적하자 소스 갱신, 종료 준비, source epoch 재바인드의 입력 off/on·수화·검증 회수에서도 사유 유실 또는 상태 고착이 재현됐다. 직접 지적된 한 줄만 고치지 않고 계획서의 전체 경계를 RED로 고정한 뒤, 호출자별 복구 의미를 보존하는 방식으로 완결했다.

세 번째 리뷰는 작업 4의 `file:exists` 3초 `Promise.race`가 호출자의 기다림만 끝낼 뿐, 막힌 `fs.promises.access()`는 main 프로세스의 libuv worker를 계속 점유한다는 P1을 찾았다. 여러 Drive 경로가 차례로 타임아웃되면 남은 작업이 누적돼 이후 파일·미디어 로드까지 줄을 설 수 있었다. 계획서 before와 현재 after는 정확히 일치했지만 실제 취소 가능한 경계는 원 계획에 없었으므로 사용자에게 계획 예외를 보고해 승인을 받은 뒤, 종료 가능한 자식 프로세스 경계로 교정했다.

### 승인 추가 작업 — 이어붙이기 전환 단일 비행

최초 부록 A-1에서 5초짜리 보조 세트는 3회 왕복했지만, 사양의 짧은 조건을 더 엄격하게 충족하는 **3초 영상 8개**에서는 이전 로드 꼬리와 다음 `ended`가 경합해 정지가 재현됐다. 이는 작업 1~6의 before 블록 불일치가 아니라, 사양 수동 검증이 드러낸 기존 전환 소유권 문제였다. 사용자 승인 후 다음 계약으로 보완했다.

- 모든 영상 로드에 단조 증가하는 intent generation을 부여해 **가장 최신 사용자 의도만** 상태를 확정한다.
- 활성 영상 로드 완료를 단일 record로 추적하고 stale/hard invalidation을 분리한다.
- 이어붙이기 전환은 세션당 하나의 flight만 실행한다. 같은 세션에서 중복 `ended`가 오면 `pendingAdvance` 하나로 합쳐 정확히 한 번만 다음 항목으로 전진한다.
- 일시정지나 오래된 비행의 정리는 새 리뷰 화면을 파괴하지 않는다. 20초 hard deadline 또는 명시적 교체만 파괴 경계의 정리 권한을 가진다.

### 승인 추가 작업 — PR 리뷰 P1 파일 probe 실제 종료

후속 Codex 리뷰에서 작업 4의 `file:exists` 데드라인이 `Promise.race`로 응답만 끝내고, 실제 `fs.promises.access()`는 main libuv worker에 남는 문제를 재현했다. 사용자가 계획 예외를 승인해 다음과 같이 보정했다.

- `main/ipc-handlers.js`: 파일 존재 확인을 별도 OS 자식 프로세스로 격리한다. Windows는 로컬 PowerShell의 고정 스크립트가 환경변수 경로를 `[System.IO.File]::Exists`·`[System.IO.Directory]::Exists`의 인자로만 읽고, 비-Windows는 Electron의 Node 실행 경계에서 `accessSync(F_OK)`를 수행한다.
- 파일 경로는 명령 문자열에 보간하지 않는다. 초기 `cmd.exe` 후보에서 따옴표가 포함된 비신뢰 IPC 값의 명령 삽입이 독립 감사로 재현돼 즉시 폐기하고, 경로를 데이터로만 취급하는 PowerShell 경계로 교체했다. 후속 감사에서 `Test-Path`가 `Env:PATH` 같은 PowerShell provider까지 존재로 인정하는 차이도 재현돼, OS 파일·폴더 API로 다시 한정했다.
- 3,000ms가 지나면 child에 `SIGKILL`을 보내고 `close` 이벤트를 확인한 뒤에만 기존 낙관적 `true`를 반환한다. 따라서 실제 응답은 `3000ms + 종료 통지 시간`이며, 이는 반환 전에 probe가 사라졌음을 보장하기 위한 의도적 차이다.
- IPC 채널·인자·boolean 반환, timeout 시 `true`, 기존 WARN 문구와 `deadlineMs: 3000`, 정상 존재 `true`·부재/시작 실패 `false` 계약은 유지했다.

## 알려진 경계와 후속 관찰점

- 이번 재개 분기는 “영상 끝에서 멈춘 상태”를 다룬다. 재생 중간에 mpv가 멈춰 `ended` 자체가 오지 않는 경우의 상시 감시는 계획서 부록 C 범위로 남겼다.
- persistence IPC와 전환 데드라인은 무한 대기를 유한 실패로 바꾸는 안전장치다. 저장 장치나 호스트가 실제로 죽은 경우에는 해당 항목이 가시적으로 건너뛰어지거나 세션이 안내와 함께 끝날 수 있다.
- WARN 이상 파일 기록으로 로그 양이 늘어난다. 배포 뒤 실사용 1일 로그 크기를 한 번 확인하는 것이 좋다.
- 3초 로컬 fixture에서는 최종 단일 비행 구현으로 24회 자동 전환이 안정적이었다. Google Drive 스트리밍 경로의 실제 네트워크 지연 조건은 별도 현장 관찰이 유효하다.
