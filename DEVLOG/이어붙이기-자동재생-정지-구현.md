사용자 관점에서 달라지는 결과는 다음과 같다.

1. 짧은 영상 여러 개를 이어붙여 반복 재생해도 이전 전환의 늦은 정리 작업이 새 영상 재생을 끊지 않는다.
2. 드로잉 저장이나 파일 확인 응답이 사라져도 앱이 무음으로 영원히 멈추지 않고, 건너뛰기·중단 안내·로그 중 하나로 원인이 보인다.
3. 전환 제한 시간으로 중단된 뒤에는 스페이스를 한 번만 눌러 다음 항목부터 다시 재생할 수 있다.
4. mpv가 실제로 전진했는지는 화면 보간값이 아니라 엔진에서 마지막으로 실측한 시각으로 판정한다.

## 배경 및 원인

실사용 로그에서 이어붙이기가 3~4회차에 멈추는 현상이 반복 확인됐다. 원인은 하나가 아니라 다음 경로가 겹친 결과였다.

- 렌더러 경고가 파일에 남지 않아 전환 실패 원인이 보이지 않았다.
- 드로잉 persistence IPC에 데드라인이 없어 응답 유실 시 전환 큐 전체가 무한 대기할 수 있었다.
- 일시적인 저장 게이트 실패도 이어붙이기 세션 전체 중단으로 승격되는 회귀가 있었다.
- `ended` 이후 비동기 전환의 예외가 격리되지 않았고 `file:exists`도 무기한 대기할 수 있었다.
- 멈춘 뒤 스페이스 첫 입력은 세션 정지만 하고 재생하지 않아 두 번 눌러야 했다.
- mpv 전진 판정이 보간 시각을 사용해 실제 엔진이 멈춰도 전진한 것으로 오판할 수 있었다.

계획서의 작업 1~6을 순서대로 적용한 뒤, 부록 A-1을 사양 그대로 3초 영상 8개로 실행했을 때 추가 경합이 실기에서 발견됐다. 이전 영상의 긴 로드 꼬리가 다음 전환 뒤늦게 살아나 새 세션의 상태를 정리하거나 같은 `ended` 요청을 중복 처리할 수 있었다. 사용자의 추가 범위 승인을 받은 뒤, 전환을 최신 사용자 의도 기준의 단일 비행으로 직렬화하는 보완 작업을 수행했다.

### 승인 추가 작업 — 이어붙이기 전환 단일 비행

최초 부록 A-1에서 5초짜리 보조 세트는 3회 왕복했지만, 사양의 짧은 조건을 더 엄격하게 충족하는 **3초 영상 8개**에서는 이전 로드 꼬리와 다음 `ended`가 경합해 정지가 재현됐다. 이는 작업 1~6의 before 블록 불일치가 아니라, 사양 수동 검증이 드러낸 기존 전환 소유권 문제였다. 사용자 승인 후 다음 계약으로 보완했다.

- 모든 영상 로드에 단조 증가하는 intent generation을 부여해 **가장 최신 사용자 의도만** 상태를 확정한다.
- 활성 영상 로드 완료를 단일 record로 추적하고 stale/hard invalidation을 분리한다.
- 이어붙이기 전환은 세션당 하나의 flight만 실행한다. 같은 세션에서 중복 `ended`가 오면 `pendingAdvance` 하나로 합쳐 정확히 한 번만 다음 항목으로 전진한다.
- 일시정지나 오래된 비행의 정리는 새 리뷰 화면을 파괴하지 않는다. 20초 hard deadline 또는 명시적 교체만 파괴 경계의 정리 권한을 가진다.
- 사용자가 즉시 스페이스로 재개하거나 재생목록을 교체하면 abandon 신호로 오래된 비행 대기자를 풀고 최신 전환을 시작한다.
- 기존 계약인 `playWhenMediaReady: true`는 유지했다. 다음 영상을 준비한 직후 자동 재생해야 하는 이어붙이기 의미를 바꾸지 않고 경합만 닫았다.
- 토큰 로컬 완료 레코드로 review settle과 뒤늦은 cleanup이 새 로드 소유권을 침범하지 않게 했다.

## 계획서와 실제 구현·검증이 달랐던 지점

1. **[사용자 승인 범위 추가] 작업 7 성격의 단일 비행 보완**
   - 원 계획은 작업 1~6만 포함했다. 모든 6개 작업을 마친 뒤 부록 A-1의 3초 영상 조건에서 정지가 재현돼 임의 진행하지 않고 사용자에게 원인과 추가 범위를 보고해 승인을 받았다.
   - 중간에는 전환 소유권, 토큰별 정리, 일시정지 화면 보존, 즉시 재개, 강제 무효화 정리를 각각 좁게 고치는 시도를 하며 RED 시나리오를 넓혔다. 그러나 개별 꼬리 정리만 막는 방식으로는 pause/resume, 같은 파일 재개, 수동 seek, 재생목록 교체가 공유하는 소유권 경합을 완전히 닫지 못했다.
   - 최종 구현은 이 실험 코드를 모두 되돌려 일관된 단일 비행 상태 기계로 교체했다. 중간 시도는 최종 동작의 누적 단계가 아니라 실패 행렬을 넓혀 최종 설계에 이르게 한 superseded 이력이다.
   - PR 전 커밋 감사에서 “작업당 커밋 1개” 규칙을 다시 적용해 승인 추가 작업도 최종 트리 그대로 한 개의 한글 `fix:` 커밋으로 통합했다. 작업 1~6과 마지막 문서·버전 커밋은 각각 별도로 유지했다.

2. **[사용자 승인 범위 추가] 원 계획의 호출 리터럴·일시정지 블록 델타**
   - 단일 비행 소유권을 전달하기 위해 `loadContinuousPlaylistItem`에 intent 인자를 추가하고 `playNextContinuousItem`에 flight 옵션을 추가했다. 이에 맞춰 두 소스 계약 테스트도 새 의미로 갱신했다.
   - 로컬·원격 일시정지에서는 물리 로드 토큰을 즉시 hard invalidate하던 호출을 제거했다. 세션 가드가 자동 재생만 막고 진행 중인 미디어 로드는 안전하게 끝내도록 해, 뒤늦은 꼬리가 정지 화면을 파괴하지 않게 한 승인 범위의 필수 델타다.
   - 보호 대상으로 지정된 Fabric 게이트 한 줄은 변경하지 않았다.

3. **[작업 4] 정상 취소 뒤 남을 수 있는 dormant timer**
   - reject된 로드 일부 경로에서 전환 감시 타이머가 즉시 clear되지 않고 최대 20초 동안 dormant 상태로 남을 수 있다.
   - 타이머는 `loadingItemId`와 session 가드를 다시 검사하므로 정상 완료 뒤에는 no-op이며, 세션을 잘못 중단하지 않는다. 의미 변경을 피하기 위해 계획 범위 밖 타이머 구조 리팩터링은 하지 않았다.

4. **[작업 5] 무시 파일이 잠시 stage된 뒤 같은 커밋에서 제거됨**
   - 서브에이전트 실행 보고서가 ignored 경로에 생성돼 잠시 stage됐지만, 제품·테스트 변경이 아니므로 커밋 amend로 제거했다. 최종 작업 5 커밋에는 `app.js`와 지정 테스트만 포함된다.

5. **[작업 6] prior status time 대신 accepted status time 가드**
   - 계획서 설명은 “prior status time 유지”라고 표현했지만, 실제 after 블록의 핵심 조건은 받아들인 mpv 상태가 존재할 때만 실측 전진을 판정하는 것이었다.
   - 구현은 `acceptedStatusTime` 가드를 사용하고 이를 고정하는 테스트를 추가했다. 보간값을 실측값으로 오인하지 않는다는 요구는 동일하며, 최초 수락 전 false positive를 더 직접적으로 막는다.
