## 배경 및 목적

레거시 드로잉 모드(캔버스 기반)에는 애니메이터가 쓰던 키프레임·레이어 단축키 16종이 있었다. mpv 파일럿(fabric 오버레이)으로 옮기면서 이 키들은 전부 **방화벽에서 차단**돼 있었다 — 누르면 아무 일도 일어나지 않는다. `docs/drawing-keyframe-features.md` 가 어느 키가 왜 막혀 있는지의 단일 참조다.

막아 둔 이유는 파일럿의 데이터 모델이 다르기 때문이다. `drawingsV3` 는 키프레임마다 오브젝트 목록만 있고 **레이어 개념이 없다.** 게다가 이 스키마는 불가침이라(레코드는 정확한 키 집합으로 3개 층에서 검증한다) 레코드에 레이어 필드를 넣을 수 없다.

그래서 이 라운드는 두 갈래로 나눴다:

- **씬 집합만 바꾸면 되는 것**(프레임 조작) → 런타임의 `targetFrame` 재키잉으로 해결(①)
- **레이어가 필요한 것** → `.bframe` **루트의 `drawingLayers`** 에 레이어 모델을 따로 두고, 오브젝트 id → 레이어 id 배정으로 그림과 잇는다(②③④⑤)

루트가 확장 가능한 것은 `shared/bframe-root-envelope.js`(2026-07-23) 덕분이다 — 앱이 모르는 최상위 필드를 원문 그대로 보존한다.

## Phase ④: 표시·잠금 (뷰 상태)

### 목표

`` ` `` 로 활성 레이어를 숨기고, `Ctrl+2` 로 잠근다. 타임라인 행의 눈·자물쇠 버튼도 같이 살린다.

### 왜 "뷰 상태" 인가

숨김·잠금은 **문서에 쓰면 안 된다.** 레코드 키 집합이 고정이라 `visible`/`locked` 를 넣을 자리가 없다. 대신:

- 레이어의 `visible`/`locked` 는 이미 `drawingLayers` 모델에 있다(②에서 만듦)
- 렌더러가 그 플래그 + 배정으로 **숨길 오브젝트 id 집합**·**잠글 id 집합**을 계산해 오버레이로 밀어 넣는다
- 오버레이는 그 집합을 들고 있다가 **씬을 그릴 때마다** 적용한다

집합을 들고 있어야 하는 이유: 프레임을 넘기거나 실행취소가 돌면 캔버스를 새로 만든다. 토글을 한 번 보내는 방식이면 그 순간 숨긴 획이 다음 프레임에서 되살아난다.

- 전체 스위트로 회귀 확인. 각 수정은 되돌려 실패하는지 확인한다

### 구현 결과 (v2.8.0-beta)

배선은 계획대로 한 방향이다: **렌더러가 계산하고 오버레이는 적용만 한다.**

```
레이어 모델(drawingLayers)  →  id 집합 계산  →  IPC  →  오버레이
 visible / locked 플래그        fabricPilotLayerViewSets()      hiddenObjectIds
 + 오브젝트 배정                                                lockedObjectIds
                                                                activeLayerDrawable
```

- 오버레이는 레이어를 모른다. `makeFabricPath` 에서 `visible` 을, `refreshSelectionInteractionPolicy` 에서 `selectable`·`evented` 를 집합으로 판정한다. 두 곳 모두를 거치므로 **캔버스를 다시 만들어도**(프레임 전환·실행취소) 유지된다.
- 활성 레이어가 숨겨졌거나 잠겼으면 `onPointerDown` 이 새 획을 받지 않는다. 선택 도구는 통과시킨다 — 다른 레이어의 획은 여전히 다뤄야 한다.
- 저장 문서는 손대지 않는다. 런타임 테스트가 숨김 적용 전후의 `exportDrawingVideo` 스냅샷이 **완전히 같음**을 단언한다.
- 호스트는 리비전·토큰·id 배열 형식·`activeLayerDrawable` 의 boolean 여부까지 검사한다. 거절은 리비전을 전진시키지 않는다.

검증: 25개 스위트 2,349 pass / 0 fail. 각 수정을 되돌려 실패를 확인했다(런타임 4건, 호스트 1건, 렌더러 3건).

### 남은 것 — Phase ⑤

``Shift+` ``(레이어 삭제)와 `Ctrl+Shift+X`·`C`(순서 이동)는 **문서를 바꾼다.** 삭제는 그 레이어의 오브젝트를 모든 키프레임에서 지우고 실행취소로 되살려야 하고, 순서는 씬의 오브젝트 순서를 레이어 순서에 맞춰 다시 배열해야 한다(새 획이 들어올 때마다 유지되어야 하므로 일회성 정렬로는 부족하다). 대조표에는 계속 **차단**으로 적혀 있다.

## Phase ⑤: 삭제·순서 (문서 변이)

### 왜 앞의 넷과 다른가

①~④ 는 **문서를 건드리지 않았다.** 프레임 조작은 씬의 `targetFrame` 집합만 바꿨고, 레이어 모델은 `.bframe` 루트의 별도 필드이며, 표시·잠금은 뷰 상태다. ⑤ 는 처음으로 `drawingsV3` 의 **오브젝트 자체**를 지우고 순서를 바꾼다. 그래서 실행취소가 얽히고, 한 프레임이 아니라 **그 영상의 모든 키프레임**에 걸린다.

### 변이 경로 열거 (먼저 한다)

④ 의 리뷰 10라운드 중 절반은 "오브젝트를 바꿀 수 있는 경로"를 한 번에 세지 않아서 한 겹씩 발견한 것이었다. 이번에는 먼저 적는다.

| # | 경로 | 지켜야 할 것 |
|---|---|---|
| 1 | 커밋된 키프레임들 | 모든 키프레임에서 그 레이어의 오브젝트를 지운다(현재 프레임만이 아니다) |
| 2 | 홀드(provisional) 씬 | 커밋 씬에서 파생되므로 조작 뒤 다시 만든다 |
| 3 | 짝인 외곽선 | 본체를 지우면 외곽선도 함께 — 고아를 남기지 않는다 |
| 4 | 활성 캔버스 | 지운 것을 걷는다. 통째로 비우면 다음 재도색에서 되살아난다 |
| 5 | 선택 | 지운 id 가 남으면 유령을 옮기거나 지운다 |
| 6 | 진행 중인 제스처 | 획·도형·라쏘·지우개·변형 — 각자 대상 목록을 들고 간다(④ 에서 배운 것) |
| 7 | 세워 둔 조각 | `pendingLassoSelection.replacements` 의 원본 id |
| 8 | 전역 실행취소 순서 | 사라진 씬의 커맨드는 걷고, 구조 항목으로 되돌린다 |
| 9 | 레이어 배정 | 지운 오브젝트의 배정은 모델에서 함께 걷는다 |
| 10 | 지속화 한도 | 삭제는 줄어들기만 하므로 새 한도 위험은 없다. 순서는 개수가 그대로다 |
| 11 | 마지막 레이어 | 모델이 거절한다(`last-layer`) — 기준 레이어는 지울 수 없다 |

### 설계

두 조작을 **한 원시 연산**으로 묶는다. 씬마다 "남길 오브젝트와 그 순서"를 정하는 것이 삭제이자 재배열이다.

- `layer-objects-remove` — 지울 id 목록을 받아 모든 키프레임에서 걷는다
- `layer-objects-reorder` — 오브젝트별 **랭크**(레이어 순서 인덱스)를 받아 각 키프레임 안에서 안정 정렬한다. 오버레이는 레이어를 모르므로 랭크만 받는다

실행취소는 ① 의 구조 히스토리를 확장한다. 지금 항목은 한 프레임의 before/after 를 들지만, 여기서는 **프레임마다** before/after 를 든다.

### 남은 결정

새로 그린 획은 여전히 맨 위에 붙는다. 레이어 순서를 지키려면 그리는 순간에도 랭크를 알아야 하므로, 랭크 맵을 표시·잠금 집합과 같은 경로로 함께 밀어 넣는다.
