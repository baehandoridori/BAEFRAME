## 배경 및 목적

2026-08-25 22:59 배포본에서 사용자가 보고한 8항목은 서로 다른 증상처럼 보였지만, 실측 결과 **뿌리가 셋**이었다.

1. **저장 실패 래치 하나가 소유권·표시·입력을 동시에 지배** — `legacyBypass` 불리언이 `shouldOwnDrawingShortcut()`의 조건항이라, 저장이라는 데이터 계층 사건이 타임라인 투영·CSS 마스크·B 라우팅을 한 번에 레거시로 되돌렸다. 2026-08-27 로그의 `invalid-persistence-snapshot`(blocked:true) 2건이 이 경로를 그대로 재현한다.
2. **차단 조건이 대상·키의 실제 소비 여부와 분리** — 문자 키를 소비하지 않는 슬라이더·셀렉트를 텍스트 입력과 동일 취급하고, 편집 대상이 없어도 IME 플래그만으로 전체 단축키를 폐기하며, 오버레이에서 릴레이된 키를 남아 있던 텍스트 포커스에 되꽂았다.
3. **일시 실패와 구조 손상을 같은 사유로 뭉갬** — 오버레이가 한 프레임 늦게 응답한 정상 상황이 영구 저장 차단 + 레거시 후퇴로 승격됐다.

## Phase 1: PR ① — 핵심 고장 (작업 1·2·3·4·6)

### 목표
증상 1·2·3·4·6을 한 번에 배포 가능 상태로. 작업 1이 나머지의 기반이므로 최우선.

### 구현 내용

**작업 1** — `shouldOwnDrawingShortcut()`에서 `legacyBypass` 참조 제거. `setPersistenceBypass()`의 세션 강제 종료(`desiredInputEnabled`/`resumeRequested`/`currentSession`/`setState('passive')`)를 `blocked === true` 분기 안으로 한정하되, `persistenceBoundSourceEpoch = null`은 저장 계층 장치이므로 분기 밖 유지. 스냅샷에 `persistenceDegraded` 별칭, 공개 API에 `clearPersistenceSaveBlock` 추가.

**작업 2** — `toggleDrawMode` 라우팅을 mpv 기준으로 고정. 가드 축을 `getState()`로 세운 것이 핵심이다 — 작업 1 이후 `shouldOwnDrawingShortcut() ≡ isEnabled()`가 되어 `if (isEnabled()) { if (!shouldOwnDrawingShortcut()) {…} }` 형태의 중첩 가드는 도달 불가능한 죽은 코드가 된다. `getFabricPilotTimelineLayers`가 레거시 `drawings`를 `pilotProjected` 읽기 전용 행으로 함께 투영하고, store 미수화 시에도 `null`을 반환하지 않는다.

**작업 3** — `consumePendingResumeRequest()` 예약 소비 단일 함수를 도입하고 정착 지점 5곳에 배선. 반환값 3분기(`null`/`false`/`Promise`)로 기존 호출부 반환 계약을 유지했다. `setDrawingInput`의 disable 반환 3경로 전부에서 `moveTop`/`invalidate`를 복원하고, 진단 restack 계약을 `Math.max(0, toggleCount-1)` → `toggleCount` 완전일치로 조였다.

**작업 4** — 비텍스트 폼 컨트롤이 실제로 소비하는 10개 코드만 차단, IME 조합 게이트를 텍스트 입력 대상에만 적용. 방화벽에서 `drawMode`를 `KeyE`·chord 차단보다 **먼저** 예외 처리하고, Ctrl chord 차단에 `event.code` 기반 조건을 OR로 더해 IME `key === 'Process'` 우회를 막았다. 호스트의 하드코딩 `'KeyB'`를 렌더러가 상태 sync로 보내는 서술자로 대체. 고아 테스트 `keyboard-shortcut-targets.test.js`를 `test:mpv`에 등록.

**작업 6** — 요청-스냅샷 펜스 불일치를 `stale-drawing-snapshot`으로 분리(비래치), 구조 위반만 `invalid-persistence-snapshot` + 차단 래치. IPC 데드라인 3000 → 8000ms. `ReviewDataManager`에 `saveStateChanged` 이벤트와 2s→5s→10s 지수 백오프. 헤더 저장 상태 칩 추가, 실패 토스트를 재시도 소진 후로 이동.

`scripts/tests/fabric-drawing-pilot-source.test.js:302`의 `assert.doesNotMatch(appSource, /fabricDrawingPilotController\.(?:getStatusSnapshot|diagnostics)\(\)/)`는 **app.js 소스 텍스트 전체**를 검사하는 HUD 폴링 금지 불변식이다. 정규식은 코드와 주석을 구분하지 않으므로, 그 리터럴을 주석에 적기만 해도 단언이 깨진다. 계획서는 두 곳 모두 "캐시 참조를 지킨 상태에서는 통과"라고 명시하고 있었으므로, **단언을 완화하는 대신 주석 표현만 바꿔 불변식을 살리는 쪽**을 택했다. 실제 코드는 계획서 의도대로 캐시 변수 `fabricDrawingPilotStatusSnapshot`을 읽는다.

## 1. 전역 modifier 래치 (작업 5 회귀)

`isCtrlActive`/`isAltActive`가 포인터 이벤트의 modifier와 오버레이 문서 전역 키 래치를 **OR**로 봤다. 래치는 `keyup`으로만 풀리는데, 오버레이는 별도 BrowserWindow이고 호스트가 키를 가로채거나 포커스가 옮겨가면 `keyup`을 놓칠 수 있다. 그 상태에서 브러시 클릭은 전부 지우개 제스처로 열려 **획이 생기지 않는다.** 래치를 푸는 경로는 `setDrawingInput`뿐이라 B 토글로만 복구됐다.

실제 fabric 하네스로 재현했다:

```
keyup 누락 시 modifierCtrl=true
그리기 시도 후 objectCount=0   ← 획이 아예 생기지 않음
```

계획서는 이 위험을 엣지 케이스 표에 적어 두고 "거짓 양성만 발생하고 blur 한 번으로 복구된다"며 수용했다. **그 판단이 틀렸다** — 거짓 양성의 실체가 "브러시가 조용히 지우개가 되는 것"이라 사용자가 원인을 알 수 없고, 앱 안에 머무르는 한 blur도 오지 않는다.

**수정**: 마우스 포인터는 modifier를 정확히 실어 오므로 이벤트 값만 신뢰한다. 전역 래치는 modifier가 비어 오는 펜·터치에만 적용하고, 마우스 이벤트가 "안 눌림"으로 오면 래치를 자가 복구시킨다(`syncOverlayModifierStateFromPointer`). 펜 경로는 그대로 유지된다.

## 2. 차단 래치를 일시 실패로 분류 (작업 6 회귀)

`persistenceBlocked`가 걸리면 `preparePersistenceSnapshotForSave()`가 영구히 `false`를 돌려주는데, app.js의 최종 스냅샷 훅이 던지는 메시지가 `TRANSIENT_SAVE_FAILURE_MESSAGES`에 걸려 **일시 실패로 분류**됐다. 성공할 수 없는 재시도를 2s→5s→10s 3회 반복하고 실패 토스트를 띄운 뒤, 사용자가 뭔가 바꿀 때마다 그 사이클이 처음부터 되풀이됐다. 실사용 로그에 두 사이클이 그대로 남아 있다.

**수정**: 훅이 차단 상태를 `saveFailureReason = 'fabric-drawing-blocked'`로 태깅하고, 이 사유를 `BLOCKING_SAVE_FAILURE_REASONS`에 넣어 재시도 없이 `save-blocked`로 한 번만 통보한다. 안내 문구도 복구 방법을 알려주도록 분기했다("영상을 다시 열면 복구됩니다").

## 3. 저장 차단의 진짜 원인 — 진단 세분화

작업 6이 넣은 `failedCheck` 로그가 계획서 진단의 오류를 드러냈다. 계획서는 실측된 `invalid-persistence-snapshot`을 **요청-스냅샷 펜스 불일치(신선도)** 로 진단하고 그것만 `stale-drawing-snapshot`으로 분리했는데, 실제 로그는 `snapshot-record` — **레코드 단계 실패**다. 즉 이번 라운드는 이 실패 자체를 고치지 못했다.

조사한 것:
- 해당 `.bframe`의 디스크 `drawingsV3`(5키프레임 34레코드)를 호스트 검증 규칙으로 전수 대조 — **위반 0건**

`snapshot-record` 하나로는 하위 검사 10종과 id 중복을 구분할 수 없어 원인 추적이 불가능했다. **수정**: `describeFabricDrawingRecordFailure()`를 추가해 어떤 검사에서 걸렸는지와 씬·오브젝트 인덱스까지 남긴다(예: `snapshot-record:point-time:7@2.3`). 레코드 내용은 남기지 않고, IPC 응답 형태도 그대로다. 다음 재현 1회로 원인이 특정된다.

# 저장 차단의 근본 원인 확정 (2026-08-27 심야, v2.4.2-beta)

v2.4.1-beta에 넣은 세분화 진단이 **한 번의 재현으로 원인을 특정**했다.

```
failedCheck: "snapshot-record:point-time:3@5.12"
           = 씬 5 · 오브젝트 12 · sourcePoints[3] 에서 point.time 역행
```

## 근본 원인 — 재생된 포인터 이벤트가 원본 시각을 잃는다

`.bframe` 저장 스키마는 **한 획의 sourcePoints 시각이 단조 증가**해야 한다는 불변식을 갖고, 스토어·런타임·호스트 세 검증기가 모두 이를 강제한다. 하나라도 걸리면 export 전체가 거절되고 저장이 차단된다.

BAEFRAME은 획 시작 시 대상 프레임을 메인에 물어 확정을 기다리고, 그동안의 포인터 입력을 스냅샷해 뒀다가 확정 후 재생한다. 그런데 `POINTER_EVENT_SNAPSHOT_FIELDS` 에 **`timeStamp` 가 없었다.** 재생 이벤트는 원본 시각을 잃고 '재생 시각'을 갖는다(`PointerEvent` 생성자는 `timeStamp` 를 무시하고 생성 시각을 넣는다).

그 결과:

```
재생된 pointerdown → time = 확정 시각 (예: 5000)
재생된 move       → 5000
재생된 move       → 5000
라이브 move       → 4990   ← 역행 (= sourcePoints[3] = point-time:3)
```

**확정 직전에 생성됐지만 확정 뒤에 배달된** 라이브 pointermove가 자기 원본 시각을 들고 오는데, 그게 재생 시각보다 이르다. 실패 지점이 정확히 점 3번인 것은 재생 표본이 끝나고 라이브 표본이 시작되는 경계이기 때문이다.

타이밍 경합이라 획을 긋는 속도에 따라 걸리기도 하고 안 걸리기도 한다 — 사용자가 보고한 "불규칙하게 발생"의 정체다. 한 번 걸리면 그 세션 내내 저장이 막힌다.

## 계획서 진단의 오류

계획서는 실측된 `invalid-persistence-snapshot` 을 **요청-스냅샷 펜스 불일치(신선도)** 로 진단하고 §7 C-4 전체를 그 위에 세웠다. 실제 원인은 **레코드의 시간 역행**이었다. 작업 6이 넣은 `failedCheck` 한 줄이 없었으면 계속 찾지 못했을 것이다. 로그로 확인되지 않은 추정 위에 설계를 세우면 안 된다는 사례로 남긴다.

## 수정

1. `POINTER_EVENT_SNAPSHOT_FIELDS` 에 `timeStamp` 추가 — 근본 원인
2. `dispatchReplayedPointerEvent` 가 생성 후 원본 `timeStamp` 를 복원 (`PointerEvent` 생성자가 무시하므로 명시적으로 되돌린다)
3. `appendPointerSample` 이 표본 시각의 단조성을 보장 — 다른 시계 이상으로도 획 하나가 파일 전체 저장을 막지 못하게 하는 방어선. `x`/`y` 는 건드리지 않아 획 모양은 불변
