# 공유 드라이브 영상 선행 읽기와 버퍼링 상태 처리

## 승인 범위

영상 전체를 변환·복사하며 기다리는 방식 없이 mpv의 빠른 시작을 유지한다. Google Drive 경로에만 선행 읽기와 메모리 상한을 적용하고, 데이터 대기 중 시간 표시 및 연속 재생이 잘못 진행하지 않도록 한다. 협업 서버 접근 정지 및 Liveblocks 오류 처리는 별도 사안이다.

## 구현 계획

1. mpv 파일별 정책: Drive 영상 앞쪽 30초, 전방 128MiB/후방 32MiB, 초기 버퍼 전체 충전 대기 없음. 기존 로컬 영상 정책 복원. 재개 최소 버퍼는 작은 값으로 검증.
2. mpv 상태에 버퍼링 및 캐시 통계 전달. 사용자 재생 의도와 실제 영상 전진을 분리해, 버퍼링 중 시간 보간을 멈추고 재개 시 실제 시간에 정렬.
3. UI에 지연 시 영상 불러오는 중 표시. 연속 재생의 진행 확인은 정상 버퍼링을 재시도/건너뛰기 실패로 처리하지 않되 취소와 유한 대기 유지. 합성 영상 동기화도 실제 버퍼 상태 반영.
4. 경로 전환·일시정지·탐색·버퍼링·복구·연속 재생 회귀 테스트, 독립 코드 리뷰, 가능한 실제 mpv/앱 검증.

## 보존과 기준

- 기준: origin/main dbc8671, v2.11.0-beta. main checkout의 다른 수정·문서와 기존 작업 공간 보존.
- 제품 코드 변경 전 실패하는 회귀 테스트로 누락 동작을 확인한다.
- 첫 화면 준비와 재생 데이터 선행 읽기를 같은 대기 조건으로 합치지 않는다.
- 리뷰 파일 경로/식별자/스키마와 원본 영상은 변경하지 않는다.
- PR 생성·머지·공유 드라이브 배포는 이번 승인에 포함되지 않는다.

## 검증 기록

### 구현

- `main/mpv-manager.js`: Windows 드라이브 루트의 `공유 드라이브`, `Shared drives`, `내 드라이브`, `My Drive` 경로에만 파일별 캐시 정책을 적용한다. 특정 드라이브 문자 전체를 Drive로 간주하지 않는다. 메타데이터 조회용 headless 로드는 제외한다.
- mpv `loadfile`의 파일별 옵션은 `cache=yes`, `cache-secs=30`, `demuxer-max-bytes=134217728`, `demuxer-max-back-bytes=33554432`, `cache-on-disk=no`, `cache-pause=yes`, `cache-pause-wait=2`, `cache-pause-initial=no`다. 이는 압축 패킷 캐시의 상한이며 프로세스 전체 메모리 상한은 아니다. 전체 30초를 채운 뒤 시작하는 조건을 추가하지 않았다.
- `VideoPlayer`: `isBuffering`, `cacheDuration`, `cacheBufferingState`, `bufferingchange`를 추가했다. `paused-for-cache`를 사용자 일시정지와 구분한다. 버퍼 대기 시 실제 관측 프레임으로 정렬하고 시간 보간을 멈춘다. 복구 시 최신 관측 시각부터 재개한다.
- 일시정지·탐색·영상 교체 전에 요청한 상태가 뒤늦게 도착해 새 상태를 덮지 않도록 요청 세대를 확인한다. 재생/일시정지 명령 처리 중의 폴링도 차단한다. 기존 프레임 이동·EOF 구간 반복을 유지한다.
- 앱의 기존 프레임 표시 자리에 `영상 불러오는 중…`을 표시한다. 합성 영상, 네이티브 합성 오버레이, 타임라인, 오디오 파형에 실제 버퍼 상태를 전달한다.
- 연속 재생 시작 확인의 기존 1.5초/3초 실패 예산에서 버퍼 대기를 제외한다. 실제 전진 없이 버퍼 대기가 누적 15초에 도달하면 현재 영상에서 연속 재생을 멈추고 안내한다. 재시도/건너뛰기 실패로 분류하지 않는다. 세션 취소 이후 늦은 이벤트도 무시한다.

### 실제 mpv와 화면 요소 확인

- 기존 번들 mpv `v0.41.0-744-g304426c39`의 별도 프로세스에서 생성한 10초 영상으로 확인했다. 실제 IPC로 8개 파일 옵션을 읽어 정책 적용을 검증했다. 같은 프로세스에서 일반 파일로 전환, 잘못된 영상 로드, 정상 영상으로 복구할 때 기본 옵션 복원을 확인했다. 종료 코드 0.
- 숨김 Electron에서 실제 HTML/CSS, `VideoPlayer`, 앱의 `bufferingchange` 리스너를 실행하고 mpv 상태만 모의 입력했다. 대기 표시의 노출/해제, 300ms 동안 프레임 고정, 최신 시각으로 재개, 사용자 일시정지 시 해제, 표시 영역 높이 유지 확인. 종료 코드 0. 이 검사는 전체 운영 앱 및 실제 네이티브 합성 영상의 E2E와 구분한다.

### 동일한 공급 지연 조건의 비교 실험

40초 생성 영상(57,611,377바이트)을 로컬 HTTP 서버로 공급했다. 연결 후 처음 4초는 평균 재생 요구량의 약 3배 속도로 공급하고, 4~12초는 공급을 멈춘 뒤 다시 공급했다. 각 조건에서 22초간 관측했다. HTTP의 기본 `cache=auto`는 네트워크 캐시를 활성화하므로 비교군은 기존 마운트 파일의 캐시 정책을 모사하도록 `cache=no`를 명시했다. 실험군은 실제 manager가 만든 파일 옵션을 추출했다.

| 관측 | 기존 정책 모사 | 새 정책 |
|---|---|---|
| 22초 동안 실제 영상 진행 | 14.875초 | 18.833초 |
| 버퍼 대기 표본(약 1초 간격, 총 23개) | 7개 | 3개 |
| 최대 선행 캐시 | 1.04초 | 11.33초 |
| 첫 프레임 준비 | 58.9ms | 42.4ms |

- 첫 프레임 숫자는 각 1회 측정으로, 속도가 향상됐다는 일반화의 근거로 쓰지 않는다. 두 조건 모두 프레임 드롭 0이었으나 headless 실행이므로 GPU/실제 화면 검증은 아니다.
- 이 조건에서는 새 정책이 약 4초 더 재생했지만 8초 공급 중단을 완전히 흡수하지는 못했다. 실제 Google Drive 처리량·지연 개선을 확정하는 실험이 아니다.
- 진단 스크립트와 원시 결과는 로컬 ignored `.superpowers/mpv-cache-runtime-probe.cjs`, `.superpowers/mpv-cache-runtime/result.json`, `.superpowers/mpv-cache-stall-comparison.cjs`, `.superpowers/mpv-cache-stall-comparison/result.json`, `.superpowers/buffering-ui-runtime/result.json`에 보관했다. 별도 서버·mpv·Electron 프로세스는 종료했다.

- 실제 Google Drive 영상으로 운영 앱에서 비교 재생하는 검증, 네이티브 합성 영상과 지연을 함께 재현하는 사용자 조작 검증은 미수행이다.

## 후속 릴리스 승인

사용자가 구현 확인 후 `배포까지 ㄱㄱ`로 PR·리뷰·머지·빌드·공유 드라이브 배포까지 승인했다. 재생 안정성 수정이므로 `2.11.0-beta`에서 `2.11.1-beta`로 패치 버전을 올린다. 팀 안내 게시와 협업 서버 설정 변경은 포함하지 않는다.

릴리스 검증을 위해 기존 합성 소스 검사 한 줄을 현재 `ReviewDataManager` 구성에 맞췄다. 이전 리뷰 기능에서 추가된 `reviewCarryoverManager`가 두 속성 사이에 존재하는 것을 검사한다. 합성 제품 코드를 추가 변경하지 않는다. 앞서 기록한 수정 전 실패와 구분해 아래에 최종 결과를 남긴다.

- `npm run test:composition` 최종: 60 pass / 0 fail / 0 cancelled, 종료 코드 0.
- `npm run test:frame-grid`: 38 pass / 0 fail / 0 cancelled, 종료 코드 0.

### PR #220 리뷰 반영

- 원격 Codex P2 `discussion_r3959387599`: 첫 시도에서 쓴 버퍼 대기 시간이 재시도에서 초기화되어 항목별 누적 15초 제한이 지켜지지 않을 수 있었다.
- `playContinuousItemWithWatchdog`가 항목별 공유 대기 예산을 생성하고 두 번의 진행 확인에 전달한다. 일반 정지 시간 계산은 각 호출에서 쓴 버퍼 시간만 제외해 원래 1.5초/3초 제한을 유지한다.
- 실제 대기 함수와 watchdog을 연결한 가상 시간 테스트로 첫 버퍼 14,120ms 이후 재시도에서 900ms를 더 기다리면 현재 항목에서 멈추고 건너뛰지 않는지 검증했다. 같은 시점에 세션이 취소되면 다른 세션에 정지·일시정지·토스트가 발생하지 않는지도 검사했다.
- 새 회귀 검증 RED: 9 pass / 1 fail → GREEN: 10 pass / 0 fail. 최종 `test:playback-buffering` 70 pass / 0 fail / 0 cancelled, `test:playlist` 330 pass / 0 fail / 0 cancelled, 모두 종료 코드 0.
- 원격 감시 스크립트가 명시 완료 댓글을 놓치며 같은 커밋에 재요청한 것을 확인하여 해당 프로세스를 종료했다. 이후 라운드는 issue comments, line comments, reviews, trigger reactions를 직접 조회하고 커밋 SHA와 대조한다. 재요청에서 발견된 위 P2도 반영한 새 커밋을 다시 검토한다.
