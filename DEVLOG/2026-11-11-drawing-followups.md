# 변형 상자 후속 — 크기 손잡이 계산 수정, 선택 유지, 조각 변형, 어니언 스킨 설정 보존, 단축키 거절 안내

브랜치 `claude/drawing-transform-followups`(기준 `316728d`, v2.14.0-beta 배포본). 2.15.0-beta 로 올린다. 앞선 작업은 [v2.14.0-beta 기록](2026-11-11-drawing-feedback-onion-transform.md)에 있다.

## 요청

v2.14.0-beta 를 배포하면서 작업 중에 발견한 개선 네 가지를 쉬운 말로 제안했고, 네 가지 모두 진행하라는 답을 받았다.

1. 어니언 스킨 설정 기억 — 앱을 다시 켜면 꺼진 상태·기본 장수로 돌아간다.
2. 옮긴 뒤에도 선택 유지 — 여러 그림을 함께 옮기면 선택이 풀려, 이어서 돌리거나 키우려면 다시 골라야 한다.
3. 잘라 고른 조각도 변형 — "부분 자르기"로 고른 조각은 옮기기만 된다.
4. 단축키 실패 안내 — 프레임 단축키가 먹지 않을 때 아무 반응이 없다.

여기에 3번을 만들다가 찾은 결함을 더했다(아래 0번). 이미 배포한 v2.14.0-beta 에 들어 있는 문제다.

## 구현

### 0. 크기 손잡이의 포인터 계산 (v2.14.0-beta 의 결함 셋)

Fabric 은 크기 손잡이를 끌 때 포인터의 **절대 위치**를 크기로 바꾼다 — (고정점에서 포인터까지의 거리 − 선택 상자의 여백) ÷ 원래 크기. 여기에 세 가지가 걸려 있었다. 큰 획에서는 눈에 잘 띄지 않고, 가는 선·작은 획·펜에서 크게 드러난다.

1. **가는 선의 굵기가 튄다.** 선택 상자의 여백(획을 잡기 쉽게 두른 6 화면 픽셀)보다 얇은 획 — 예를 들어 굵기 3 의 가로선 — 에서 아래쪽 손잡이(왼쪽 아래·오른쪽 아래·아래 변)를 잡고 조금만 움직여도 굵기가 3배로 튄다. Fabric 7.4.0 의 `getLocalPoint` 가 여백을 걷어낼 때 세로 방향의 한 줄이 잘못돼 있다.

   ```js
   if (localPoint.y >= padding) localPoint.y -= padding;
   if (localPoint.y <= padding) localPoint.y += padding;   // -padding 이어야 한다
   ```

   여백을 뺀 값이 다시 여백 이하면 도로 더해진다. 가로 방향은 맞게 돼 있다.
2. **납작해지는 구간에서 도로 커진다.** 포인터가 고정점에서 여백 안쪽으로 들어오면 Fabric 은 그 좌표를 그대로 크기로 쓴다. 그래서 손잡이를 고정점 쪽으로 당기면 크기가 0 까지 줄었다가 그 구간에서 도로 커진다. 큰 획에서는 6% 이하라 보이지 않지만, 굵기 3 의 선은 손잡이를 3 픽셀만 당겨도 그 구간이고 굵기가 두 배 가까이로 뛴다(가로 방향에도 있는 Fabric 의 원래 동작이다).
3. **손잡이의 어디를 잡았는지 보지 않는다.** 한가운데에서 벗어나 잡은 만큼이 첫 걸음에 그대로 크기에 얹힌다. 손잡이의 판정 영역은 마우스·펜이 9 화면 픽셀이라 최대 4.5 픽셀이다(Fabric 7.4.0 은 펜을 터치로 치지 않는다. 터치는 26 픽셀이라 13 픽셀까지다). 100 픽셀짜리 획에서는 4.5% 지만 20 픽셀짜리 획에서는 22%, 굵기 3 의 선에서는 굵기가 0 이 되거나 2.5 배가 된다. 회전과 이동은 원래부터 잡은 자리를 기준으로 한다.

수정(`resolveScalePointer`): 크기 손잡이의 동작을 감싸, 다듬은 좌표를 넘기고 그 계산 동안 오브젝트의 `padding` 을 0 으로 둔다(Fabric 이 여백을 한 번 더 건드리지 않게).

- 조작의 첫 걸음에 잡은 자리(`transform.ex`·`ey`)와 손잡이 한가운데(고정점에서 크기 + 여백만큼 떨어진 곳)의 차이를 재 두고, 이후의 포인터에서 그만큼을 뺀다. 판정 영역보다 큰 값이 나오면 믿지 않는다.
- 여백을 걷어내되, 여백 안쪽은 크기 0 으로 붙인다(조작 한계 0.02 배에 멈춘다). 0 을 그대로 넘기지는 않는다 — Fabric 이 첫 걸음의 부호를 "원래 방향"으로 기억하므로, 첫 걸음이 그 구간에 떨어지면 방향을 반대로 기억해 이후의 움직임을 뒤집기로 보고 막는다. 부호를 남긴 아주 작은 값을 넘긴다.
- 돌린 획은 회전을 푼 축에서 계산한 뒤 화면 좌표로 되돌린다. 여러 획을 고른 묶음에는 여백이 없지만 잡은 자리의 어긋남은 똑같이 덜어 낸다.
- 계산할 수 없으면(Fabric 의 해당 함수가 없다) 손대지 않고 Fabric 의 계산에 맡긴다.

왜 놓쳤나: v2.14.0-beta 의 크기 검사는 전부 대각선 획의 손잡이 **한가운데**를 끌었다(경계 상자가 60×40 이라 1·2 에 걸리지 않고, 한가운데라 3 도 걸리지 않는다). 3번을 만들면서 "끌었다가 제자리에 놓으면 아무것도 바뀌지 않는다" 를 가로선의 조각으로 검사하다가 세로 배율이 1 로 돌아오지 않아 1 이 드러났고, 그 수정을 다시 읽으면서 2·3 을 찾았다.

수정을 하나씩 꺼 보고 그 수정을 지키는 테스트가 실패하는 것을 확인했다: 잡은 자리 보정 → "손잡이를 한가운데에서 벗어나 잡아도…", 여백 안쪽 붙이기와 부호 남기기 → "가는 선을 고정점 쪽으로 바짝 당기면…", 포인터 다듬기 전체 → 가는 선 네 건 모두.

### 1. 어니언 스킨 설정 보존

팔레트 값 보존(v2.13.0-beta)과 같은 통로를 하나 더 냈다.

- `shared/fabric-onion-skin-prefs.js`(신규): 한도·기본값·검증(`normalizeFabricOnionSkinPrefs`). 형식이 조금이라도 다르면 null 이고 고쳐 쓰지 않는다.
- 오버레이 → 메인: 런타임 `setOnionSkin` 이 켜짐·장수·진하기가 실제로 달라졌을 때 `mpvOverlayOnionSkinPrefs.notify` → `mpv-overlay:onion-skin-prefs`(발신자 확인 + 검증) → `fabric-drawing:onion-skin-prefs` → 메인 창이 모아서 `userSettings.setFabricOnionSkinPrefs` 로 적는다(저장을 모으는 모듈은 팔레트 것을 그대로 쓴다). 재생 여부는 설정이 아니라 알리지 않는다.
- 메인 → 오버레이: 상태가 보기·그리기가 될 때마다 `pushFabricPilotOnionSkinPrefs` → `mpv:apply-overlay-onion-skin-prefs` → 호스트 `applyDrawingOnionSkinPrefs`(토글·재생 알림과 같은 줄) → 런타임 `applyOnionSkinPrefs`. 기본값 그대로면 보내지 않는다. 심는 일은 따로 시험할 수 있게 모듈로 뺐다(`renderer/scripts/modules/fabric-onion-skin-prefs-pusher.js`): 아직 적지 못한 변경을 먼저 적고, 오버레이가 답하지 않았으면(준비 전이라 버려졌다·전송 실패) 0.5·1.5·4초 뒤에 다시 보내며, 새로 심기 시작하면 앞선 재시도는 그만둔다.
- 원본은 오버레이다. 사용자가 그 런타임에서 값을 한 번이라도 바꿨으면 저장값을 거절하고, 받은 값은 되받아 알리지 않는다.
- 런타임의 한도·기본값 상수를 공유 모듈에서 받게 했다. ES 모듈인 `user-settings.js` 만 리터럴을 따로 두고 테스트가 값이 같음을 강제한다.

### 2. 여러 획을 옮긴 뒤에도 선택 유지

- 예전에는 여러 획을 옮기면 선택을 풀었다(`scheduleMovedMultiSelectionRelease`, 2026-07-21). Fabric 의 묶음이 자식 좌표를 묶음 기준으로 들고 있어 그대로 두면 다음 조작이 낡은 기준에서 시작하기 때문이다.
- 이제는 씬을 다시 세우고 같은 것을 다시 고른다(`reselectMovedMultiSelection`). 크기·회전을 저장한 뒤의 처리와 같다. 잘라 고른 조각 여러 개를 옮긴 뒤(`commitPendingLassoMove`)에도 같다.
- 씬을 다시 세우면(`canvas.clear()`) Fabric 이 진행 중인 변형을 끝내면서 `object:modified` 를 한 번 더 낸다. 세 경로(옮기기·조각 옮기기·조각 변형) 모두 그 알림을 받지 않게 표시해 둔다(`ignoreLateModifiedEvents`). 조각 옮기기는 그동안 표시 없이도 한 번만 저장됐는데, Fabric 이 선택을 풀면서 묶음을 먼저 비워 두 번째 알림이 "고른 것 없음"으로 끝났기 때문이다 — 우연에 기대지 않게 했고, 테스트가 실행취소 한 단계·변경 한 번임을 확인한다.
- 바뀐 점: 묶음의 상자 안에서 끌면 묶음이 통째로 움직인다. 그 안의 획 하나만 따로 잡으려면 먼저 빈 곳을 눌러 선택을 푼다. 옛 동작을 전제한 테스트 일곱 건을 새 동작으로 고쳤다(가짜 캔버스로 "선택 풀기 예약" 을 본 세 건은 "예약이 없고 한 번만 저장한다" 는 한 건으로 합쳤다).

### 3. 잘라 고른 조각의 변형

- 부분 선택으로 세워 둔 조각은 아직 문서에 없는 프록시다. 옮길 때는 처음 움직이는 순간 원본 획을 조각으로 갈아 끼우고(`materializePendingLassoSelection`), 손을 떼면 가르기와 이동을 한 번에 저장한다. 크기·회전도 같은 순서로 얹었다.
- `selectionAllowsTransform` 이 세워 둔 선택과 정확히 같은 묶음이면 변형 상자를 준다.
- `onObjectTransforming` 이 처음 변형되는 순간 조각으로 갈아 끼우고 외곽선 짝을 짓는다. 외곽선 프록시는 그때 처음 캔버스에 올라와 변형 전 그대로지만 본체는 이미 첫 걸음만큼 변형돼 있으므로, 본체의 출발 행렬은 `before:transform` 에서 적어 둔 것(`pendingBodyStartMatrices`)을 쓴다.
- `commitPendingLassoTransform` 이 `replaceObjects({ replacements, selectedObjectIds, transforms })` 로 한 번에 저장하고(스토어는 원래 `transforms` 를 받는다) 씬을 다시 세운 뒤 조각을 다시 고른다. 바뀐 것이 없으면 획을 가르지 않는다.
- 갈아 끼우기와 외곽선 짝짓기는 한 함수(`materializePendingLassoForTransform`)로 모았다. 변형 중에도 저장 직전에도 그 길로 들어와, 어느 쪽이 먼저 오든 외곽선 짝이 빠지지 않는다.
- 저장을 그만두는 경우(제자리에 놓았다·배율 한도 밖·스토어 거절·그 사이 문서가 바뀌었다)는 `abandonPendingLassoCommit` 하나로 모았다. 화면과 외곽선을 조작 전으로 되돌리고, 늦게 오는 `object:modified` 를 받지 않게 표시한 뒤 세워 둔 선택을 걷는다. 조각 옮기기의 실패 경로도 같은 함수를 쓴다.

### 4. 프레임 단축키 거절 안내

- 컨트롤러 옵션 `onFrameOperationRejected({ action, reason })`. 단축키 경로(`applyFrameOperationFromShortcut`)에서 오버레이가 사유를 붙여 거절했을 때만 부른다. 요청을 만들지 못해 보내지도 않은 경우(`invalid-request`)는 오버레이의 답이 아니라 알리지 않는다.
- app.js 의 `FABRIC_PILOT_FRAME_OPERATION_REJECTIONS` 가 사유를 문구로 바꾼다. 표에 없는 사유에는 아무것도 띄우지 않는다. 테스트가 표의 사유마다 오버레이가 실제로 그 값을 돌려주는지 확인한다(낡은 문구 방지).

## 저장 형식

`drawingsV3` 와 `.bframe` 은 바뀌지 않았다. 새로 생긴 저장값은 사용자 설정의 `drawingOnionSkin`(이 PC 전용) 하나다.

## 독립 리뷰

코덱스 리뷰와 별개로, 구현 맥락을 주지 않은 리뷰 에이전트 둘에게 변경분을 나눠 맡겼다(그리기 엔진 / 설정 보존·안내). 둘 다 major 는 없다고 답했고, minor 7건·nit 4건 가운데 아래를 반영했다. 반영분은 하나씩 꺼 보고 그 수정을 지키는 테스트가 실패하는 것을 확인했다.

| 지적 | 처리 |
|---|---|
| 조각 변형의 저장이 실패했을 때 화면이 돌아오는 것은 우연이었다(늦게 오는 `object:modified` 가 "고른 것 없음"으로 끝나면서 되돌렸다) | `abandonPendingLassoCommit` 으로 명시했다. 스토어가 거절하는 경우를 테스트로 고정했다(문서·실행취소·화면·외곽선 모두 조작 전 그대로) |
| 조각 변형이 이 조작의 출발 기록 없이도 저장을 진행한다(외곽선이 옛 모양으로 저장될 수 있다) | 출발 기록이 그 대상의 것이 아니면 저장하지 않는다 |
| 세워 둔 선택의 변형 허용이 레이어 숨김·잠금을 따로 보지 않는다 | 원본 획의 id 로 확인한다 |
| 크기 계산 중에 여백 값이 바뀌면 낡은 값으로 덮는다 / 첫 걸음에 예외가 나면 잡은 자리를 나중에 잰다 | 0 그대로일 때만 되돌린다 / 재지 못했으면 어긋남 없음으로 둔다 |
| 복원이 오버레이에 닿지 못한 채 값을 바꾸면 보존해 둔 장수·진하기를 기본값이 덮는다 | 닿지 못했으면 다시 보낸다(세 번). 끝내 닿지 못하는 경우는 한계로 남긴다(팔레트 값 보존과 같다) |
| `timeline-full` 문구("영상 끝에 그림이 있어…")가 빈 키프레임일 때 맞지 않는다 | "마지막 프레임에 키프레임이 있어 프레임을 더 넣을 수 없습니다" |
| `scene-capacity-exceeded` 는 프레임 삭제에서도 나온다("더 넣을 수 없습니다"가 어색하다) | "그림이 너무 많아 이 조작을 할 수 없습니다" |
| 컨트롤러가 스스로 붙인 `invalid-request` 로도 안내 콜백이 불린다 | 걸러 낸다 |

반영하지 않은 것:

- 저장할 수 없는 변형을 한 뒤 세워 둔 조각의 선택이 풀린다(일반 선택은 남는다). 조각 옮기기의 기존 규칙(저장하지 못하면 선택을 걷는다)과 같게 뒀다. 세워 둔 상태로 되돌리려면 조각을 다시 세워야 한다.
- 종료 직전의 마지막 변경이 설정 파일에 닿지 못할 수 있다(파일 쓰기가 비동기다). 팔레트 값 보존과 같은 기존 구조이고 확인되지 않은 지적이라 이번 범위에 넣지 않았다.

실제 앱 조작(2026-11-11, 커밋 `77659ab` 와 같은 소스로 만든 후보 빌드 `dist/win-unpacked/BFRAME_alpha_v2.exe` — 커밋 직전의 작업 폴더에서 빌드했다. 격리 프로필, 640×360 24fps 시험 영상). Playwright 로 패키지된 앱을 띄우고 메인 창에는 키 입력을, 오버레이 창에는 마우스 입력을 DevTools 프로토콜로 넣었다. 전 항목 통과, 페이지 오류 0건.

| 항목 | 확인한 것 |
|---|---|
| 프레임 단축키 거절 안내 | 패널을 닫은 채 복사 없이 Ctrl+Alt+V → 토스트 "복사해 둔 프레임이 없습니다" |
| 가는 선의 모서리 손잡이 | 굵기 3 의 가로선을 고르고, 오른쪽 아래 손잡이를 **한가운데에서 2 픽셀 벗어난 곳**에서 잡아 옆으로 60·아래로 12 화면 픽셀 끌었다. 그림의 폭 162 → 196(기대 +33.9), 높이 2 → 9(기대 +6.8) 캔버스 픽셀. 끈 만큼만 변한다 |

점검 스크립트가 세 번 헛짚었다(앱의 결함은 아니었다).

- 가는 선의 모서리 손잡이를 커서 모양(`se-resize`)으로 찾으려 했는데, Fabric 은 손잡이 커서를 오브젝트 한가운데에서 본 방향으로 정해 길쭉한 선의 모서리에는 가로 커서(`e-resize`)를 준다. 동작은 정상이고 커서 모양만 그렇다. 손잡이를 자리로 찾게 고쳤다.
- 묶음을 옮기려고 가로선의 한가운데를 잡았더니 그 자리가 묶음 상자의 위쪽 변 손잡이였다(선이 상자의 위쪽 변에 걸쳐 있다). 옮기기가 아니라 세로 크기 조절이 됐고, 그 결과 자체는 맞았다. 상자 안쪽의 그림을 잡게 고쳤다.
- 다시 켠 직후 곧바로 `1` 을 눌렀더니 받아들여지지 않았다. 저장된 그림을 읽는 동안에는 컨트롤러가 준비 상태라 단축키를 받지 않는다(다른 단축키도 같고, 이번 변경 전에도 같다). 타임라인에 저장된 그림이 올라온 뒤에 누르게 고쳤다.

미확인:

- 실물 마우스·키보드로 사람이 직접 조작하는 확인(위 조작은 자동 입력이다).
- 실물 펜 태블릿: 손잡이를 펜으로 잡는 감각, 펜으로 Shift 를 누른 채 끌기(v2.14.0-beta 때와 같다).
- 다른 PC 와의 동시 편집 중 변형.
- 종료 직전에 바꾼 어니언 스킨 값이 다음 실행에 남는지(위 점검은 파일에 적힌 것을 확인한 뒤에 껐다).

## 남은 일

- 손잡이 커서: 길쭉한 획의 모서리 손잡이에 대각선이 아니라 가로(또는 세로) 커서가 뜬다. Fabric 의 기본 동작이고 v2.14.0-beta 에도 있다. 모서리의 방향으로 정하게 바꿀 수 있다.
- 회전 중심점 이동·기울이기·뒤집기는 여전히 없다.
