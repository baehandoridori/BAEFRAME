# 합성 레이어가 `(로컬 충돌)` 사본으로 복제됨 — 옛 사본과 삭제를 가리는 수정 횟수·삭제 표시

브랜치 `claude/composition-layer-conflict-copies`(기준 `e18134f`, v2.16.3-beta). 2.16.4-beta 로 올린다.

## 요청

2026-11-18, 해결 표시 조사(`DEVLOG/2026-11-18-comment-resolve-realtime.md`) 중에 팀 전체가 함께 여는 검수용 `.bframe` 에서 합성 레이어가 이름 끝에 `(로컬 충돌)` 이 붙은 사본 네 개로 남아 있는 것을 봤다. 그때는 "옛 사본에 없는 것을 삭제로 읽어 로컬 수정과 충돌 → 사본" 이라고 추정만 하고 손대지 않았다. 원인을 확정하고 고친다. 하이라이트·레거시 드로잉 갈래도 같은 문제가 있는지 함께 본다.

## 조사

### 파일에 남은 흔적 (16:23 KST 사본, 읽기 전용으로 구조만 분석)

- 합성 레이어 4개는 서로 다른 레이어가 아니라 **레이어 하나의 사본 넷**이다. id 는 같은 원본 id 에 `__local-conflict`, `__local-conflict-2`, `-3`, `-4` 가 붙어 있고 원본 id 는 없다. 그림(클립보드 캡처 임베드)·구간·이름이 모두 같고 **위치와 크기만 서로 다르다.** 레이어를 옮기거나 크기를 바꿀 때마다 사본이 하나씩 생긴 모양이다.
- 레코드의 칸 구성과 순서는 지금 앱이 쓰는 것과 같다(`sourceDuration: 0` 포함). 저장 모양 차이의 흔적은 없다.
- 하이라이트 0개, 레거시 드로잉 레이어 1개(키프레임 0개).

### 코드

- `(로컬 충돌)` 을 붙이는 곳은 `review-data-manager.js` 의 `createDeterministicConflictCopy` 하나이고, 부르는 곳은 공용 병합 `mergeEntityCollectionThreeWay` 의 "기준과 로컬에는 있고 원격에는 없으며, 로컬이 기준과 다르다" 갈래다. 합성 레이어·하이라이트·레거시 드로잉·댓글 레이어·수동 버전이 이 함수를 그대로 쓴다(댓글 마커만 v2.16.3-beta 에서 따로 판정하게 됐다).
- 저장은 화면의 모델을 바꾸지 않고(병합 결과는 파일에만 쓴다), 저장 뒤의 병합 기준은 "저장 직전의 로컬" 이다.
- 합성 레이어는 실시간 전송(Broadcast)이 없다. 연결 중에는 파일이 바뀌어도 합성 레이어를 다시 읽지 않는다(드로잉·이어받기·댓글만 읽는다). 그래서 연결 중인 사용자의 화면과 기준에는 처음 연 때의 레이어가 끝까지 남는다.
- 레이어 레코드에는 수정 시각도 삭제 표시도 없다. 순서 번호(`order`)는 레코드 안에 있고 병합이 끝나면 자리대로 다시 매긴다.
- 합성 레이어 매니저는 영상 레이어의 변환 확인이 끝나면(저장되지 않는 화면 상태) `changed` 를 낸다. 저장 매니저는 `changed` 를 모두 문서 변경으로 친다.

## 원인

수정 전 코드에서 실패하는 재현 검사로 각각 확인했다.

1. **옛 사본에 없는 레이어를 삭제로 읽는다.** 내 저장을 아직 못 본 PC 의 저장분이 드라이브에 나중에 올라가면 그 파일에는 내 레이어가 없다. 병합은 이것을 "원격이 지웠다" 로 읽는다. 그 뒤 내가 그 레이어를 고쳐 저장하면 "원격은 지우고 로컬은 고쳤다" 가 되어 `…__local-conflict` 사본으로 바꿔 쓴다. 고치지 않았으면 조용히 지운다(파일 동기화로 일하는 PC 는 화면에서도 사라진다).
2. **그 뒤로는 고칠 때마다 사본이 하나씩 는다.** 저장은 화면을 바꾸지 않으므로 화면과 기준에는 원본 id 가 그대로 있고 파일에는 사본만 있다. 다음 편집도 "기준과 로컬에는 있고 원격에는 없다" 로 읽혀 `-2`, `-3`, `-4` 가 생긴다. 실제 파일의 네 사본이 이 순서로 정확히 재현된다(검사 `레이어를 고칠 때마다 사본이 하나씩 늘지 않는다`).
3. **옛 사본이 레이어를 이전 상태로 되돌리고, 그 위에서 또 고치면 `(원격 충돌)` 사본이 생긴다.** 레코드에 수정 시각이 없어 "예전 값" 이 원격의 새 변경으로 읽힌다.
4. **순서 번호가 바뀐 것만으로 "고쳤다" 로 읽는다.** 다른 사람이 레이어를 끼워 넣으면 내 레이어의 `order` 가 파일에서 바뀐다. 연결 중인 내 화면의 `order` 는 그대로라, 그 레이어를 고치는 순간 "양쪽이 고쳤다" 가 되어 `(원격 충돌)` 사본이 생긴다.
5. **영상 레이어는 저장 반복을 만든다.** 영상 레이어가 든 파일은 열기만 해도(변환 확인이 끝나면) 저장이 걸린다. 파일 동기화로 일하는 PC 는 자기 저장도 파일 감시에 잡혀 파일을 다시 읽고, 다시 읽으면 변환 확인이 다시 돌아 또 저장한다 — 저장 → 다시 읽기 → 저장이 끝없이 되풀이된다(검사에서 회전마다 저장 1회). 이 저장들이 다른 PC 에는 옛 사본이 된다.

처음의 추정과 견주면: "옛 사본에 없는 것을 삭제로 읽어 로컬 수정과 충돌 → 사본" 은 맞았다. 다만 레이어 넷이 각각 사본이 된 것이 아니라 **레이어 하나가 고칠 때마다 복제된 것**이었고(원인 2), 그 바탕에는 연결 중에 합성 레이어를 파일에서 다시 읽지 않는 구조가 있었다. "같은 레이어의 저장 모양 차이" 는 원인이 아니었다 — 앱이 쓴 레코드는 열었다 저장해도 바이트까지 같다. 다만 조사 중에 매니저의 정규화가 한 번으로는 자리 잡지 않는 칸을 하나 찾았다(`sourceDuration` 이 없으면 null, 그 null 은 다음 정규화에서 0). 앱이 만든 레코드에는 생기지 않는 모양이지만, 그런 레코드를 가진 파일에서는 이전 코드가 손대지 않은 레이어를 "고쳤다" 로 읽는다.

### 고른 것과 고르지 않은 것

- **수정 시각이 아니라 수정 횟수.** 댓글은 "이 인스턴스가 들고 있던 상태와 똑같은 원격은 옛 사본" 으로 가리고 앞뒤를 수정 시각으로 정했다. 합성 레이어는 레코드에 수정 시각이 없어, 들고 있던 상태만으로 가리면 Ctrl+Z 로 예전과 똑같아진 레이어가 옛 사본으로 읽히고 두 PC 가 서로의 저장분을 번갈아 덮어쓴다(댓글 작업의 "재확인 3" 과 같은 함정). 레이어마다 횟수를 두면 되돌려도 횟수가 오르고, PC 시계와 무관하며, 어느 PC 에서 계산해도 같다. 그래서 화면으로 받아들일 때와 파일에 쓸 때의 판정을 나눌 필요가 없었다. 이어받기(`shared/review-carryover.js` 의 `generation`)가 같은 이유로 같은 방식을 쓴다.
- **레코드가 아니라 루트의 별도 키.** 레코드에 칸을 더하면 이전 버전이 저장할 때마다 손대지 않은 레이어를 "내가 고쳤다" 로 읽는다(레코드를 정해진 칸만으로 다시 쓰고, 기준은 파일의 모양 그대로 든다). 그러면 섞여 쓰는 동안 이전 버전 PC 에서 충돌 사본이 더 많이 생긴다. 루트의 모르는 키는 이전 버전도 읽은 그대로 다시 쓴다(`drawingLayersV1` 과 같은 자리).
- **한쪽이 지우고 다른 쪽이 고치면 고친 레이어가 남는다.** 이전에는 고친 쪽을 `(원격 충돌)`/`(로컬 충돌)` 사본으로 보존했다. 사본을 만들면 화면의 id 와 파일의 id 가 갈라져 위 원인 2 가 되풀이된다. 고친 레이어를 제 id 로 남기고 삭제 표시보다 뒤로 찍는다(지운 사람의 화면에는 레이어가 고쳐진 채로 돌아온다).
- **두 사람이 같은 레이어를 함께 고치면 한쪽이 통째로 이긴다.** 칸 단위로 섞지 않는다(댓글과 같다). 사본은 만들지 않는다.
- **수정 횟수가 같고 내용이 다른데 내가 고친 것이 아니면 파일 쪽을 받고 다시 저장하지 않는다.** 이전 버전은 수정 횟수를 올리지 않으므로 이렇게 해야 이전 버전의 수정이 전해진다. 여기서 "내 것이 맞다" 며 저장하면 서로 다른 내용을 든 두 PC 가 끝없이 번갈아 저장한다.
- **연결 중 받아들이기를 넣었다.** 합성 레이어는 전송이 없어 이 경로가 없으면 화면과 파일이 세션 내내 갈라져 있고(원인 2 의 바탕), 파일이 옛 사본으로 돌아가도 다음 저장 때까지 바로잡지 않는다.
- **"남의 편집을 삭제로 덮지 않는다" 는 지운 사람이 본 판과 견준다.** 처음에는 병합 기준과 견줬다("기준 뒤에 파일이 바뀌었으면 남의 편집"). 그러면 기준이 내 저장분보다 뒤처진 순간마다 — 쓰는 사이에 화면에서 또 손을 댔을 때, 쓰기는 끝났는데 저장이 실패로 처리됐을 때 — 방금 내가 쓴 것이 남의 편집으로 읽혀 지운 레이어가 되살아난다(아래 "리뷰" 의 1). 삭제 표시에 "지울 때 화면에 있던 판" 을 메모리로만 기억해 두고 그것과 견주면 기준이 어디 있든 답이 같다.
- **삭제 표시가 있으면 목록에 남아 있어도 삭제다.** 처음에는 "목록에 있으면 살아 있다" 로 읽었다. 이 앱은 그런 파일을 쓰지 않지만 웹 뷰어가 쓴다(예전에 연 목록 + 최신 파일의 별도 칸). 살아 있다고 읽으면 웹 뷰어가 댓글 하나를 저장할 때마다 그 사이 지운 레이어가 모든 PC 에서 되살아난다.
- **수정 횟수를 적을 수 없는 파일에서는 수정 횟수를 쓰지 않는다.** `compositionLayerSyncV1` 의 판 번호가 더 높으면 그 값을 읽지도 쓰지도 않는다. 처음에는 그 상태에서도 메모리의 수정 횟수·삭제 표시로 판정했는데, 같은 파일을 연 두 PC 가 서로 자기 것이 나중이라고 읽어 끝없이 번갈아 저장했다("리뷰" 의 2). 기준과의 비교만으로 합치고 파일을 바로잡으려 들지 않는다 — 옛 사본을 가리지 못하는 대신 저장이 멈춘다.
- **하이라이트·레거시 드로잉에는 삭제 표시를 넣지 않았다.** 아래 "다른 갈래" 참고.
- **이미 파일에 생긴 사본은 건드리지 않는다.** 어느 사본이 맞는 위치인지는 만든 사람만 안다.

## 다른 갈래

- **하이라이트**: 같은 공용 병합을 쓰고 실시간 전송도 없다. 같은 순서에서 주석 끝에 ` (로컬 충돌)` 이 붙은 사본이 저장할 때마다 늘었다. 공용 병합을 고쳐 사본은 더 생기지 않는다(검사 `하이라이트·레거시 드로잉도…`). 남은 것: ① 손대지 않은 하이라이트가 옛 사본에 없으면 지워진다(삭제 표시가 없다). ② 하이라이트 id 가 PC 마다 1부터 매기는 순번(`highlight-1`)이라, 두 사람이 각자 만든 하이라이트의 id 가 겹쳐 한쪽이 주석에 ` (원격 충돌)` 이 붙은 사본이 된다. ③ 내가 지운 하이라이트를 다른 사람이 그 사이 고쳤으면 ` (원격 충돌)` 사본으로 돌아온다(이전과 같다). 실제 `HighlightManager` 로 확인만 했다. 합성 레이어와 같은 방식으로 고치려면 id 부터 겹치지 않게 바꿔야 해서 이번 범위에 넣지 않았다. 하이라이트는 연결 중에 파일에서 받아들이지도 않는다.
- **레거시 드로잉 레이어**: 같은 공용 병합. 지금 앱에서는 레거시 드로잉을 그릴 수단이 없어(표시 전용) 로컬 수정이 생길 일이 드물다. 공용 병합 수정이 같이 적용된다.
- **댓글 레이어·수동 버전**: 공용 병합 수정이 같이 적용된다. 원격에 없는데 내가 고친 원소가 `…__local-conflict` 사본 대신 제 id 로 남는다.
- **답글**: 예전 동작(사본)을 그대로 둔다. 답글은 지운 쪽이 "내가 들고 있다 지운 id" 를 되살리지 않으므로(v2.16.3-beta 의 `hasSeenReply`), 고친 답글을 제 id 로 남기면 지운 쪽에서 버려지고 그 결과가 고친 쪽으로 돌아와 **고친 내용이 모두에게서 사라진다.** 공용 병합을 고친 첫 판이 이 회귀를 만들었고 독립 검토가 찾았다("리뷰" 의 9).
- **웹 뷰어**: 합성 레이어를 보여 주지도 고치지도 않지만, 저장할 때 `compositionLayers` 는 자기가 연 때의 것을 다시 쓰고 모르는 키는 최신 파일에서 가져온다(`web-viewer/scripts/bframe-write-guard.js`). 그 사이 데스크톱에서 추가한 레이어는 지켜지고(데스크톱이 파일을 바로잡는다) 지운 레이어는 삭제 표시로 지켜지지만, **고친 레이어는 예전 내용으로 되돌려진다**(수정 횟수는 최신인데 내용만 옛것이라 가릴 수 없다. 이전과 같은 동작). 웹 뷰어가 최신 파일의 `compositionLayers` 를 그대로 두도록 고치면 없어진다 — 웹 뷰어는 `main` 에 들어가는 즉시 따로 배포되는 경로(`.github/workflows/deploy-web-viewer.yml`)라 이번 변경에 넣지 않고 후속 작업으로 제안한다.

### 재확인

수정분을 같은 두 검토자에게 다시 보였다. 처음의 11건은 재현 스크립트에서 모두 사라졌고(웹 뷰어의 "고친 레이어" 는 한계로 남긴 그대로), **고치면서 생긴 문제**를 네 건 더 찾았다. 모두 재현 검사를 먼저 넣고 고쳤다.

- **가. 삭제 표시가 한도를 넘으면 두 PC 가 끝없이 번갈아 저장한다**(한도를 2로 낮춘 사본에서 확인. 실제로는 삭제 표시가 512개를 넘어야 한다). 4번에서 넣은 "빠진 삭제 표시를 다시 적는다" 가 원인: 같은 레이어를 두 PC 가 서로의 삭제를 못 본 채 각자 지우면 지운 시각이 다르고, 각자 자기 값을 들고 있어 "최근 것부터 한도만큼" 의 순위가 갈린다. 서로 "내 표시가 빠졌고 적을 수 있다" 로 읽는다. → 같은 레이어의 삭제 표시는 어느 PC 에서나 같은 값으로 모이게 하고(수정 횟수가 큰 쪽, 같으면 더 나중에 지운 쪽), 파일의 삭제 표시가 한도에 차 있으면 빠진 표시를 다시 적지 않는다. 한도 2 사본의 무작위 시험: 고치기 전 250가지 중 7가지가 멈추지 않음 → 고친 뒤 수치는 "실행 기록".
- **나. 내가 쓴 것인데 수정 횟수만 올라간 저장분을 남의 편집으로 읽는다.** 다른 사람의 삭제 표시(수정 횟수 3)를 내 편집(1)이 이기면 내 내용이 수정 횟수 3 으로 쓰인다. 그 쓰기 도중에 지우면, 파일의 3 이 "지울 때 보던 판" 의 1 보다 커서 못 본 편집으로 읽혔다 — 두 사람이 다 지운 레이어가 양쪽 화면에 남는다. → 내용이 지울 때 보던 것과 같으면 수정 횟수와 무관하게 "보고 지운 것" 으로 본다.
- **다. 화면 전용 변경(영상 레이어의 변환 확인이 끝남)이 저장을 한 번씩 더 일으킨다.** 8번을 "변경 이벤트가 왔을 때 아직 파일과 맞춰 보지 않은 내 변경이 있으면 저장할 변경" 으로 고쳤는데, 저장이 파일을 쓰는 사이나 내 편집이 더 나중 수정에 진 직후에는 그 조건이 잠깐 참이라, 그때 온 화면 전용 변경마다 저장이 걸렸다(되풀이되지는 않는다). → 변경 이벤트 쪽은 원래대로 두고, 저장이 실패한 자리에서 표시한다.
- **라. 10초 뒤의 강제 받아들이기가 실제 조작에 끼어든다.** 키보드로 이름을 고치면 확정한 뒤에도 다음 클릭까지 "조작 중" 표시가 남아(창의 pointerup 으로만 풀렸다), 그동안의 받아들이기가 모두 10초씩 밀렸고, 길게 입력하는 중이면 입력 칸이 다시 그려졌다. → 패널의 값이 확정되는 순간 조작을 끝낸다(원인). 강제 받아들이기는 표시가 풀리지 않고 남은 경우만을 위한 것이므로 30초로 늘렸다.

재확인에서 확인만 하고 그대로 둔 것: 웹 뷰어가 저장할 때마다 열려 있는 데스크톱이 한 번씩 다시 저장한다(그 사이 지운 레이어의 옛 레코드를 치우느라. 되풀이되지 않는다) · 삭제 표시가 있는 레코드가 든 파일을 열기만 해서는 그 레코드를 치우지 않는다(다음 저장 때 치운다) · 새 버전이 이미 지운 레이어를 이전 버전에서 지웠다가 되돌리면 새 버전이 다시 치운다.

검토가 찾았지만 이번 변경과 무관해 고치지 않은 것(둘 다 `e18134f` 에도 있다. 후속 작업으로 제안):

- `reloadAndMerge` 가 겹쳐 돌면 `isLoading` 이 켜진 채로 굳어, 그 뒤의 편집이 저장할 변경으로 표시되지 않는다.
- 다음 영상의 `.bframe` 을 읽다 실패하면 앞 영상의 합성 레이어가 화면에 남고, 첫 저장이 그것을 다음 영상의 파일에 합쳐 쓴다.

## 남은 한계

- **새 버전을 띄운 사람에게만 적용된다.** 이전 버전(2.16.3-beta 이하)을 켜 둔 PC 는 예전처럼 사본을 만들 수 있고, 새 버전은 그 사본을 새 레이어로 받는다. 섞여 있는 동안:
  - 이전 버전에서 **지운** 합성 레이어는 새 버전 사용자가 그 파일을 열고 있으면 되살아난다(삭제 표시가 없어 옛 사본으로 읽는다). 새 버전으로 다시 지우면 된다.
  - 이전 버전에서 **고친** 레이어는 받아들이지만, 예전처럼 옛 사본에 되돌려질 수 있다(수정 횟수가 오르지 않는다).
  - 새 버전이 지운 레이어를 이전 버전(연결 중)이 화면에 든 채로 고치면 `(로컬 충돌)` 사본이 생긴다.
- **웹 뷰어로 저장하면, 웹 뷰어를 연 뒤에 데스크톱에서 고친 합성 레이어가 예전 내용으로 돌아갈 수 있다**(이전과 같다. "다른 갈래" 의 웹 뷰어). 추가한 레이어와 지운 레이어는 지켜진다.
- **이미 파일에 있는 사본은 그대로 있다.** 아래 "이미 생긴 사본의 정리" 참고.
- **같은 레이어를 두 사람이 몇 초 안에 고치면 한쪽 변경이 통째로 이긴다.** 사본은 생기지 않는다.
- **지운 레이어를 다른 사람이 같은 때 고치고 있었으면 레이어가 되살아난다.** 다시 지우면 된다.
- **앱을 끈 사이의 덮어쓰기는 막을 수 없다.** 내 레이어가 든 저장분이 다른 PC 의 옛 사본에 덮였는데 그 레이어를 가진 PC 가 하나도 켜져 있지 않으면 되살릴 곳이 없다(이전과 같다). 삭제도 같다 — 삭제 표시까지 덮였는데 그 삭제를 아는 PC 가 모두 꺼져 있으면 레이어가 돌아올 수 있다.
- **옛 사본이 늦게 내려오면 그보다 새 상태를 가진 PC 가 한 번씩 다시 저장한다**(댓글과 같다).
- **다른 사람의 레이어 변경을 받아들이면 합성 레이어의 되돌리기(Ctrl+Z) 기록이 비워진다.** 파일 동기화로 일할 때는 원래 그랬고, 연결 중에는 이번에 받아들이기가 생기면서 같아졌다.
- **받아들이기를 미룬 지 30초가 지나면 조작 중이어도 받아들인다.** 조작 표시가 풀리지 않고 남은 경우를 위한 것이다. 실제로 30초 넘게 끌거나 입력하는 중이었다면 거기에 끼어든다(그때까지 옮긴 위치·입력한 값은 내 편집으로 남고, 입력 칸의 포커스와 되돌리기 기록을 잃는다).
- **웹 뷰어가 저장할 때마다 열려 있는 데스크톱이 한 번씩 다시 저장할 수 있다**(웹 뷰어를 연 뒤에 지운 레이어가 있으면 그 옛 레코드를 치우느라).
- **`compositionLayerSyncV1` 의 판 번호가 이 앱이 아는 것보다 높은 파일**(앞으로의 버전이 쓴 파일)에서는 이 앱이 옛 사본을 가리지 못한다(이전 버전과 같은 동작, 사본은 만들지 않는다).
- **연결 중의 파일 변경마다 파일을 한 번 더 읽는다**(드로잉·이어받기·댓글에 더해 네 번째). 한 번 읽은 것을 나눠 쓰게 고칠 수 있지만 이번에는 하지 않았다.
- **하이라이트·레거시 드로잉의 손대지 않은 원소는 옛 사본에 지워질 수 있다**("다른 갈래").

## 이미 생긴 사본의 정리 (제안)

자동으로 지우지 않는다. 사본마다 위치·크기가 다르고 어느 것이 맞는지는 만든 사람만 안다.

1. 새 버전으로 그 파일을 열고 합성 레이어 패널에서 사본들을 하나씩 켜고 꺼 보며 남길 것을 고른다(대개 마지막으로 옮긴 위치의 사본).
2. 나머지를 패널에서 지운다(우클릭 → 삭제). 새 버전에서 지우면 삭제 표시가 남아 옛 사본이 내려와도 되살아나지 않는다.
3. 남긴 사본의 이름에서 ` (로컬 충돌)` 을 지운다(우클릭 → 이름).

어느 파일에 사본이 있는지 찾아야 하면, 공유 폴더의 `.bframe` 을 읽기만 해서 `-conflict` 가 든 id 를 세는 스크립트를 만들어 돌릴 수 있다(요청이 있을 때).
