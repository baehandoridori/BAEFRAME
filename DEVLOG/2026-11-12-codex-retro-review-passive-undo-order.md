`renderer/scripts/modules/fabric-drawing-pilot-controller.js` 의 `rememberPassiveHistory` ([댓글](https://github.com/baehandoridori/BAEFRAME/pull/238#discussion_r4546627537)):

> 그리기 패널을 닫은 상태에서 프레임 조작을 보내고 응답이 오기 전에 댓글 편집 등 전역 이력이 추가되면, 응답 처리 시점의 리비전이 이전 프레임 조작에 붙는다. 그래서 프레임 조작을 가장 최근 작업으로 잘못 판단하고, 다음 Ctrl+Z 에서 나중에 한 댓글 편집 대신 프레임 조작을 되돌린다. (요약)

## 대조

지적은 맞다.

- 패널을 닫은 채 한 프레임 조작은 오버레이의 구조 히스토리에 들어가고, 컨트롤러는 응답으로 받은 표식(`historyToken`)을 전역 히스토리 리비전과 함께 기억한다. Ctrl+Z 는 **맨 위 표식의 리비전이 지금의 리비전과 같을 때만** 그 조작을 되돌리고, 아니면 전역 실행취소로 넘긴다(`peekPassiveHistory`). 리비전을 **응답이 온 때** 읽고 있었다.
- 그래서 [프레임 조작 요청 → 전역 작업 → 프레임 조작의 응답] 순서가 되면 표식에 전역 작업 **뒤**의 리비전이 붙어, 먼저 한 프레임 조작이 마지막으로 한 일로 보인다. Ctrl+Z 를 두 번 누르면 둘 다 되돌아가기는 하지만 순서가 뒤바뀐다.
- 걸리려면 응답을 기다리는 사이(보통 수십 밀리초, 오버레이가 바쁘거나 큐에 앞선 조작이 있으면 더 길다)에 전역 작업을 해야 한다. 드물다.
- 요청한 때의 값으로 바꿔도 되는지: 전역 리비전을 올리는 것은 `pushUndo`(댓글·마커·하이라이트 등), 사용자가 직접 한 전역 실행취소·다시 실행, 파일 전환뿐이다(`app.js` 의 `advanceGlobalHistoryRevision` 호출부). 프레임 조작 자신은 전역 히스토리에 아무것도 넣지 않으므로 요청과 응답 사이에 스스로 리비전을 올리지 않는다. 정상 흐름은 달라지지 않는다.
- 같은 모양이 한 군데 더 있었다. 되돌리기·다시 실행의 응답 뒤에 표식을 반대쪽 스택으로 옮기면서도 응답 때의 리비전을 붙였다. 되돌리기의 응답을 기다리는 사이에 새 전역 작업이 생기면, 새 작업 뒤인데도 Ctrl+Y 가 그 되돌리기를 다시 실행했다. 봇이 짚은 곳은 아니지만 같은 결함이라 함께 고쳤다.

**봇이 제안한 대로만 고치면 다른 순서가 깨진다.** 제안은 "요청한 때의 리비전을 보존하고, 기다리는 사이에 전역 히스토리가 바뀌었으면 그 표식을 최신 작업으로 등록하지 않는다"였다. 그렇게만 바꾸고 변경분을 다시 따져 보니 [프레임 조작 → Ctrl+Z(응답 전이라 받아 둠) → 전역 작업 → 응답] 순서에서 받아 둔 Ctrl+Z 가 아무 일도 하지 않게 됐다. 큐에서 그 키를 판정할 때 "지금의 리비전"과 견주기 때문이다 — 표식(요청한 때의 값)과 지금의 값이 달라 프레임 조작을 되돌리지 않고, 전역 실행취소는 키를 누른 뒤에 히스토리가 바뀌었다는 이유로 막힌다. 이 순서는 고치기 전에는 (응답 때의 값이 우연히 맞아) 프레임 조작을 되돌렸다. 검사로 먼저 재현한 뒤 판정 기준을 고쳤다.

정리한 규칙은 하나다: **무엇이 마지막으로 한 일인지는 키를 누른 때를 기준으로 본다.**

| 순서 | 고치기 전 | 지금 |
|---|---|---|
| 프레임 조작 → 응답 → Ctrl+Z | 프레임 조작을 되돌림 | 같음 |
| 프레임 조작 → Ctrl+Z → 응답 | 프레임 조작을 되돌림 | 같음 |
| 프레임 조작 → 응답 → 전역 작업 → Ctrl+Z | 전역 작업을 되돌림 | 같음 |
| 프레임 조작 → 전역 작업 → 응답 → Ctrl+Z | **프레임 조작을 되돌림(순서가 뒤집힘)** | 전역 작업을 되돌림 |
| 프레임 조작 → 전역 작업 → Ctrl+Z → 응답 | **프레임 조작을 되돌림(순서가 뒤집힘)** | 전역 작업을 되돌림 |
| 프레임 조작 → Ctrl+Z → 전역 작업 → 응답 | 프레임 조작을 되돌림 | 같음(봇의 제안대로만 고치면 아무 일도 하지 않는다) |
| …→ Ctrl+Z(되돌리기) → 전역 작업 → 되돌리기의 응답 → Ctrl+Y | **프레임 조작을 다시 실행** | 다시 실행하지 않음 |

고친 뒤에도 두 히스토리(오버레이의 구조 히스토리와 전역 히스토리)의 순서를 완전히 하나로 합치지는 않는다. 프레임 조작 뒤에 전역 작업을 하고 Ctrl+Z 를 두 번 누르면, 두 번째는 프레임 조작이 아니라 그 앞의 전역 작업으로 간다(v2.14.0-beta 부터의 설계다).

## 수정

- `applyDrawingActionDetailed`: 요청을 만드는 자리에서 `readHistoryRevision()` 을 읽어 둔다. 큐에서 차례를 기다리는 시간과 응답을 기다리는 시간 모두 그 뒤다.
- `notePassiveFrameOperation` → `rememberPassiveHistory(historyToken, revision)`: 읽어 둔 값을 표식에 붙인다.
- `peekPassiveHistory(direction, revision)`: 견줄 리비전을 받는다. 키를 누른 자리(`routeKeydown`)에서는 지금의 값이고, 큐에서 차례가 온 키(`applyPassiveHistoryAction`)는 **누를 때 읽어 둔 값**(`historyRevision`)을 넘긴다. 누른 뒤에 생긴 전역 작업은 그 키보다 나중의 일이다. 되돌릴 대상은 표식으로 집으므로 늦게 실행해도 엉뚱한 것을 되돌리지 않는다(오버레이의 맨 위가 그 표식이 아니면 오버레이가 거절하고, 그때는 지금처럼 표식을 전부 버린다).
- `applyPassiveHistoryAction`: 반대쪽 스택으로 옮기는 표식에 `entry.revision`(위 판정에서 키를 누른 때의 값과 같음을 확인한 값)을 그대로 둔다.

`readHistoryRevision` 이 읽기에 실패하면 매번 다른 객체를 돌려주므로(fail-close) 표식은 지금처럼 쓰이지 않는다.
