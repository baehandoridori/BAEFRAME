## 작업 1 — Alt 브러시 크기 조절 복구 (PR ①)

### 배경

v2.4.3-beta 실기에서 Alt를 누른 채 드래그해도 브러시 크기가 변하지 않았다.
단위 테스트는 통과하고, **Ctrl 드래그 임시 지우개는 정상 동작**했다. 이 비대칭이 결정적 단서였다.

### 근본 원인

Windows 마우스 메시지(`WM_LBUTTONDOWN` 등)의 `wParam`에는 `MK_CONTROL`·`MK_SHIFT`가 실려 오지만
**Alt에 해당하는 플래그가 없다.** Chromium은 Alt 상태를 마우스 메시지가 아니라 **그 창(스레드)의
키보드 입력 큐**에서 얻는다. 오버레이가 키보드 포커스를 가진 적이 없으면 Alt keydown이 그 큐에
들어간 적도 없으므로, Alt+드래그가 `altKey:false`로 도착해 `isAltActive()`가 `false`를 돌려주고
크기 조절 분기에 진입하지 못한다.

`main/mpv-overlay-host.js`의 두 경로가 비대칭이었다.

- `updateDrawingTool()`은 도구 변경이 확정되면 **이미 `hostWindow.focus()`를 호출**하고 있었다.
- 그런데 그리기 입력을 켜는 `_setNativeDrawingInput(hostWindow, true)`에는 `focus()`가 없었다 —
  `setFocusable(true)`로 "포커스 가능"하게만 만들고 실제로 주지 않았다.

즉 **그리기 중 오버레이가 포커스를 갖는 것은 이미 의도된 정상 상태였는데, 진입 경로만 그것을 보장하지 않았다.**

### 배제한 원인 (다시 조사하지 말 것)

문서 `docs/drawing-keyframe-features.md` §7.1이 적은 착수점 4가지 중 3가지를 배제했다.

| 착수점 | 판정 | 근거 |
|---|---|---|
| ② `before-input-event`가 Alt를 삼키는가 | **아니다** | `FORWARDED_NAMED_KEY_CODES`에 `AltLeft`/`AltRight`가 없어 `createForwardedKeyboardInput()`이 `null`을 반환하고 `preventDefault`도 일어나지 않는다 |
| (추가) 번들이 소스보다 낡았는가 | **아니다** | 재생성 후 diff 0, 제스처 코드 22건 존재 |
| ④ HUD가 오버레이 밖에 그려지는가 | **아니고 증상과도 무관** | HUD `zIndex:3` > 팔레트 `zIndex:2`. 증상은 "HUD가 안 보인다"가 아니라 "크기가 안 변한다"였다 |

### 수정

**(a)** `_setNativeDrawingInput` enable 경로 마지막에 `hostWindow.focus?.()` 추가.
`moveTop()`·`invalidate()` **뒤**에 둔다 — 앞에 두면 네이티브 확장 스타일 변경이 포커스를 도로 가져갈 수 있다.

**(b)** 제스처 진단 계측. 문서 §7.1은 *"`getDiagnostics().gestures`로 관측 가능"*이라고 적었으나
**사실이 아니었다.** `getDrawingDiagnostics()`가 런타임 진단을 필드 단위 화이트리스트로 중계하는데
`gestures` 블록이 목록에 없어 **통째로 버려지고 있었다.** 실기에서는 애초에 아무것도 볼 수 없었다.

- 호스트에 `sanitizeFabricGestureDiagnostics()` 신설 — 값 범위를 고정한 채 중계
- 런타임에 `gestureProbe` 추가 — 오버레이 Alt/Ctrl keydown 횟수 + 마지막 pointerdown의 modifier 출처
  (`altKey` / 래치 / `pointerType` / `documentHasFocus` / 재생 여부)

**표본 채취 순서가 계약이다.** `syncOverlayModifierStateFromPointer()`가 마우스 경로에서 래치를 지우므로
`recordPointerdownProbe()`를 **그보다 먼저** 불러야 "래치가 있었는지"가 남는다. 테스트가 이 순서를 고정한다.

### 다음 재현에서 원인을 가르는 표

| `gestures.lastPointerdown.altKey` | `gestures.overlayAltKeyDownCount` | 결론 |
|---|---|---|
| `true` + `altSizeAdjustActive: true` | 무관 | 이번 수정으로 해결됨 |
| `false` | `0` | 오버레이가 Alt keydown을 받은 적 없음 → 포커스 문제 |
| `false` | 1 이상 | 오버레이는 Alt를 받는데 마우스 이벤트에만 안 실림 → Windows 메시지 계층 |

### 계획서와 실제가 달랐던 지점

없다. 계획서의 before 블록은 전건 문자 단위로 일치했고, **계획서가 예고한 기존 테스트 1건만 정확히 실패했다.**

`scripts/tests/mpv-overlay-host.test.js`의 `overlay.focus` 호출 횟수를 **정확히 1**로 세는 단언이다.
enable 경로가 포커스를 되돌리게 되면 2가 된다. **단언을 완화하지 않고** 기대값을 2로 올리고 설명 문자열을
갱신했다 — 이 단언은 "포커스 복원이 몇 번 일어나는가"를 세는 계약이고, 숫자가 늘어나는 것이 수정의 의도다.

신규 테스트를 작성하며 계획서 대비 2가지를 조정했다.

1. 진단 중계 테스트를 **"정상 중계"와 "`gestures` 부재 시 `null`" 두 건으로 분리**했다. 경계를 더 정확히 고정한다.
   그래서 신규가 계획서의 5건이 아니라 **6건**이 됐고, 부록 B 델타를 실측치로 정정했다.
2. `enabling drawing input focuses the overlay` 테스트에서 `moveTop`은 창 수명 초반(ensure/show)에도
   불리므로 `names.indexOf('moveTop', ignoreFalseIndex)`로 **enable 구간 이후만** 보게 했다.

### 실기 확인 필요 (부록 A의 A-1 ~ A-5)

이번 배포의 핵심 목적은 **Alt 원인 확정**이다.

1. `B`로 그리기 모드 진입 → **곧바로** Alt 누른 채 좌우 드래그 → 크기가 변하고 `NNpx` HUD가 뜬다
2. Alt 우클릭 드래그 → 컨텍스트 메뉴가 뜨지 않고 크기만 바뀐다
3. Ctrl 드래그 → 기존대로 지나간 획이 지워진다 (회귀 없음)
4. Alt 드래그 직후 일반 드래그 → 획이 정상적으로 그려진다 (래치 stuck 없음)
5. 그리기 모드에서 `Space`·`←`/`→` → 메인 창 단축키가 여전히 동작한다 (포커스 획득의 부작용 확인)

1번이 되면 원인이 확정되고 수정도 끝난 것이다. 여전히 안 되면 위 판별표로 다음 조치를 정한다.
