# 코멘트·드로잉·저장·공유 UX 감사 근거

- 조사일: 2026-09-06 (Asia/Seoul)
- 조사 기준: `main`, `v2.9.0-beta`, `d72f6b7a87af9e5805eb03a0e0a6017bba999f32`
- 범위: 코멘트 생성·범위·검색·해결, 드로잉 발견성, 저장·재열기 경계, 공유 및 협업 상태, 다른 버전의 리뷰.
- 조사 중 제품 코드 변경 없음. 증거 파일은 임시 폴더에서 보존한 사본이며 SHA-256 일치를 확인했다.
- 본 파일의 최초 근거는 소스 조사와 자동 실행 결과다. 이후 보고서 작성 담당자의 실제 Windows 앱 관찰·스크린샷·저장 파일을 검토하여 R2와 R3를 보강했다(§7). 두 PC 협업·Google Drive 전달 성공은 증명하지 않는다.
- 배포 웹 뷰어의 현재 코드 확인은 이 하위 조사 범위 밖이며, 보고서의 별도 웹 조사 증거와 구분한다.

## 1. 우선순위와 발견

### R1. 공유 전 저장 실패를 성공처럼 알림 — P1, 결함

**사용자 영향:** 최신 피드백이 파일에 저장되지 않았거나 첫 리뷰 파일 생성에 실패한 상태에서 경로를 전달할 수 있다. 화면은 자동 저장 및 복사가 성공했다고 알려 사용자가 문제를 알아차리기 어렵다.

**근거:**

- `renderer/scripts/app.js:3260-3274`: `await reviewDataManager.save()` 반환값을 검사하지 않고 `.bframe 파일이 자동 저장되었습니다.` 토스트를 표시한다. 예외가 발생해도 링크 복사는 계속한다.
- 같은 파일 `3321-3326`: 경로 복사 후 성공 토스트를 표시한다.
- `renderer/scripts/modules/review-data-manager.js:1404,1486,1626,1634`: 저장 지연 및 실패 경로는 예외뿐 아니라 `false`를 반환한다.
- 대조 사례: `renderer/scripts/app.js:11089-11098`의 피드백 가져오기는 저장 반환값을 확인하고 화면 추가와 저장 실패를 구분한다.

**함수 실행 결과:** 현행 클릭 핸들러를 소스에서 추출하고 파일 없음·미저장 변경 있음·`save() => false`로 실행했다. 실제 파일이나 클립보드는 변경하지 않고 stub으로 호출만 기록했다. 저장 성공 토스트와 경로 복사 호출이 모두 발생했다.

**개선안:** 저장 성공과 공유 가능한 파일 상태를 확인한 뒤 안내한다. 저장 실패 시 초안을 유지하고 재시도 동작을 제공한다.

**수용 기준:** `false`, 예외, 파일 생성 지연 각각에서 잘못된 저장 성공 안내가 나오지 않는다. 사용자가 전달할 리뷰의 상태를 확인할 수 있다.

### R2. V3 그림이 댓글 작성과 웹 보기 경계에서 빠짐 — P1, 앱 표시 결함 및 웹 구현 제한

**사용자 영향:** 앱에서 그린 내용을 보며 댓글을 작성하려는 순간 그 그림이 사라질 수 있다. 웹 수신자에게도 그림이 빠져 리뷰 의도가 불완전하게 전달될 수 있다. 이번 실제 앱 관찰에서는 댓글 모드 취소 후 같은 프레임에 그림이 다시 나타났으므로 저장 데이터 삭제가 아닌 표시 경로 문제로 분류한다.

**A. 앱의 하이브리드 댓글 모드 — 실제 화면·현재 소스 대조:**

- 실제 앱의 테스트 영상 C, frame 33, 약 1.376초에 저장한 빨간 획 1개가 댓글 모드 진입 후 HTML5 화면에서 보이지 않고, 취소 후 mpv 복귀 화면에서는 다시 보였다. [댓글 작성 중](../assets/07-comment-hybrid.png)과 [취소 후 복귀](../assets/08-comment-cancel.png)를 직접 열어 같은 Frame 33의 표시 차이를 확인했다.
- `renderer/scripts/app.js:2536-2552`: mpv에서 댓글 모드 진입 시 하이브리드 전환을 시도한다. `8564-8579`: 설정이 켜져 있고 HTML5로 직접 재생 가능한 코덱이면 같은 파일을 engineSwap=true, initialFrame 유지, playWhenMediaReady=false로 연다.
- `renderer/scripts/modules/user-settings.js:214,777`: 하이브리드 리뷰 엔진의 기본값은 켜짐이다.
- `renderer/scripts/modules/video-player.js:418-425`: HTML5 load는 기존 external stop을 호출하고 엔진을 HTML5로 바꾼다. 앱의 external stop(`app.js:10159,10098-10102`)은 `stopMpvPilotEngine:9956-9971`을 거쳐 `destroyMpvPilotHosts:9947-9953`에서 mpv 오버레이를 제거한다.
- `renderer/scripts/modules/fabric-drawing-pilot-controller.js:1248-1249`: V3 표시 컨텍스트는 isMpvActive=true만 유효하다. passive 표시도 `374-388`에서 이 조건을 확인한다.
- `renderer/scripts/app.js:6604-6608,6749`: HTML5에서는 V3 레이어 투영이 null이 되고 레거시 drawingManager의 레이어로 내려간다. 로드 완료 시 `10916-10917`은 drawingManager.renderFrame을 실행한다.
- `renderer/scripts/modules/drawing-manager.js:1552,1577-1583`: 정지 화면의 캔버스를 비우고 레거시 keyframe.canvasData를 합성한다. drawing-manager와 drawing-canvas 소스에는 V3 참조가 없다.
- `renderer/scripts/app.js:10846-10860`: engineSwap은 같은 파일의 리뷰 데이터를 다시 읽거나 초기화하지 않고 메모리에 유지한다. 이번 증거는 이 보존과 맞으며 데이터 삭제를 주장할 이유가 없다.

**B. 웹 보기 — 소스·유효 네이티브 파일의 함수 실행:**

- `main/ipc-handlers.js:1241,1280`: 공유 URL을 `https://baeframe.vercel.app/open.html`로 생성한다.
- `web-viewer/scripts/app.js:2017-2029`: 프레임의 그림을 렌더링할 때 `state.bframeData.drawings`만 읽고 배열이 아니면 반환한다.
- 위 웹 뷰어 소스에는 `drawingsV3` 참조가 없다.
- mpv 그림 루트의 저장·수신 처리는 `renderer/scripts/modules/review-data-manager.js:2436` 이후의 V3 경로에 있다.

**함수 실행 결과:** 처음에는 V3 존재만 표시한 sentinel로 분기를 확인했다. 후속으로 실제 앱이 저장한 [native-drawing-sample.bframe](native-drawing-sample.bframe)을 현행 V3 persistence store에 넣어 accepted=true, frame 33, 객체 1개를 확인했다. 이 유효 파일을 현행 로컬 웹 렌더 함수에 같은 프레임으로 전달해도 clear 1회·paint 0회다. [실행 코드](review-native-sample-check.cjs)와 [결과](review-native-sample-check-result.log), exit 0을 보존했다.

**개선안:** 댓글 작성 중에도 같은 프레임의 기존 V3 그림을 유지한다. 하이브리드 전환에 V3 표시 경로를 연결하거나, V3 그림이 있는 문서에서는 현재 표시가 유지되는 리뷰 경로를 사용한다. 웹에서도 V3·레이어·홀드의 읽기 전용 표현을 지원한다. 레거시 drawings에 이중 저장하는 방식으로 우회하지 않는다.

**수용 기준:** 그리기→댓글 입력→취소/등록→다시 보기 사이에 같은 프레임의 획·도형·레이어 숨김·홀드가 유지된다. 앱과 웹의 읽기 결과도 일치한다. 하이브리드 꺼짐·지원 불가 코덱은 대조 조건으로 포함한다. 배포본·실제 공유 계정·미디어 접근은 별도 확인한다.

### R3. 댓글 전송 후 위치 지정 취소 시 초안 유실 — P1, 결함

**사용자 영향:** 전송 버튼이 등록 완료처럼 보이지만 실제로는 마커 위치 선택을 시작한다. 글과 이미지 미리보기를 입력창에서 먼저 제거하므로, 위치를 찍기 전에 모드를 취소하면 입력 본문을 잃을 수 있다. 본 하네스가 확인한 유실 대상은 텍스트이며 첨부 이미지의 후속 상태는 별도 검증이 필요하다.

**근거:**

- `renderer/scripts/app.js:3121-3135`: 본문을 pending에 저장한 뒤 입력창을 비우고 이미지 미리보기를 제거한다.
- `renderer/scripts/modules/comment-manager.js:451-454`: 댓글 모드 해제 시 pendingText를 제거한다.
- `renderer/scripts/app.js:11459-11463`: 그리기 모드 진입은 댓글 모드를 해제한다.
- `renderer/scripts/app.js:11904-11915`: 마커의 본문 입력 중에도 바깥 클릭으로 포커스를 잃으면 댓글 모드를 해제한다.

**함수 실행 결과:** 현행 사이드바 제출 함수와 CommentManager를 실행했다. 제출 직후 입력은 빈 문자열, pending은 본문, 등록 수는 0이었다. `setCommentMode(false)` 후 입력은 빈 문자열, pending은 null, 등록 수는 0이었다.

**후속 실제 앱 결과:** 보고서 작성 담당자의 [native-comment-draft.json](native-comment-draft.json)에 본문 입력→전송 후 입력 빈칸·댓글 0→위치 지정 전 취소 후 입력 빈칸·댓글 0이 기록되어 있다. 해당 JSON을 직접 읽어 함수 재현과 일치함을 확인했다. 이 증거는 댓글 버튼으로 취소한 경로이며 모든 Esc·바깥 클릭·이미지 경로를 대신하지 않는다.

**개선안:** 실제 등록까지 초안을 보존한다. 위치 지정 단계를 계속 표시하고 취소하면 원래 입력으로 되돌린다.

**수용 기준:** 텍스트·이미지 작성 → 위치 지정 시작 → Esc/그리기 전환/바깥 클릭 후 초안을 복원할 수 있다. 실제 UI 취소 경로별 검증은 추가로 필요하다.

### R4. 이전·다음 댓글 이동과 목록 필터가 다름 — P2, 설계 개선

**사용자 영향:** 미해결만 보는 중 해결된 댓글로 이동할 수 있다. 재생목록 전체 댓글 목록에 다음 컷 댓글이 있어도 버튼의 탐색 범위는 현재 영상이다. 기존 버튼이 전체 영상 마커를 순회하도록 설계되었을 가능성을 배제할 수 없으므로, 명시 사양을 위반한 결함보다는 리뷰 흐름을 통일하는 개선으로 분류한다.

**근거:**

- `renderer/scripts/app.js:3076-3110`: 이전·다음 버튼은 현재 CommentManager의 프레임 탐색 메서드만 호출한다.
- `renderer/scripts/modules/comment-manager.js:882-912`: 두 탐색 메서드는 전체 마커를 검사하며 필터 인자를 받지 않는다.
- `renderer/scripts/app.js:13388-13400`: 목록은 상태·작성자·검색 필터를 적용한다.
- 같은 파일 `13369-13372`: 재생목록 모드의 목록은 재생목록 전체 집계 흐름으로 전환된다.

**함수 실행 결과:** 해결된 frame 24와 미해결 frame 96을 넣으면 미해결 필터의 대상은 96뿐이지만 현재 `getNextMarkerFrame(0)`은 24를 반환한다. 재생목록 전체 이동은 소스 조사 결과이며 실기 전환 재현은 수행하지 않았다.

**개선안:** 목록과 이동 버튼의 대상 집합을 통일한다. 필터가 켜져 있다면 그 결과를 따라 이동하고, 재생목록 전체 목록에서 컷 경계를 넘어갈 수 있게 한다.

**수용 기준:** 미해결·작성자·검색 필터의 표시 순서와 이전·다음 결과가 일치한다. 현재 컷 뒤에 남은 댓글이 있으면 올바른 파일·프레임으로 이동한다.

### R5. 단축키 안내와 mpv 기능 지원 상태가 불일치 — P2, 결함 및 구현 제한

**사용자 영향:** 안내를 따라 키를 눌러도 다른 기능이 실행되거나 반응이 없어 조작 실수 또는 앱 오류처럼 느껴진다.

**근거:**

- `renderer/index.html:1213`: 그리기 단축키를 D로 안내한다. 실제 `renderer/scripts/modules/user-settings.js:31`은 B, `53`의 D는 다음 키프레임이다.
- `renderer/index.html:806,814`: 댓글 이동 버튼은 Shift+좌우 화살표를 안내한다. 실제 `user-settings.js:22-23`과 `renderer/scripts/app.js:15158,15165`는 빠른 프레임 이동으로 처리한다.
- `renderer/scripts/app.js:1611-1630`: 힌트 갱신 함수는 위 설명문과 댓글 이동 버튼을 갱신하지 않는다.
- F6/F7/Delete 키프레임 기능은 설정에 남아 있지만 `app.js:6307-6309,6373-6413,14649-14652`의 Fabric/레거시 단축키 차단 대상이다. Delete는 먼저 선택 획 삭제에 쓰일 수도 있어 키프레임 삭제와 구분해야 한다.

**개선안:** 사용자 설정의 액션에서 모든 힌트를 생성한다. 현재 엔진의 미지원 기능에는 대체 조작과 지원 상태를 표시한다.

**수용 기준:** 기본값, 사용자 재지정, mpv 활성 상태 각각에서 안내·버튼·키보드 동작이 일치한다. 미지원 액션이 동작 가능한 기능처럼 제시되지 않는다.

### R6. 연결됨과 리뷰 전달 완료의 구분 — P2, 설계 제안

**사용자 영향:** 사용자가 동기화 완료라는 안내를 상대방에게 최신 리뷰가 반영되었다는 뜻으로 받아들일 수 있다.

**근거:**

- `renderer/scripts/app.js:18497-18505`: 연결 상태가 connected이면 synced 표시를 설정한다.
- 같은 파일 `18267-18269`: synced 툴팁 문구는 동기화 완료다.
- 같은 파일 `18509-18515`: 수동 동기화 버튼은 상태 문구만 표시한다.

**개선안:** 이 PC에 저장됨, 실시간 연결됨, 상대에게 반영됨처럼 상태가 보장하는 범위를 구분한다. 전달 확인을 구현하지 않았다면 연결 상태 문구로 표현한다.

**수용 기준:** 네트워크 단절·재연결·Drive 지연 상황에서도 안내가 실제 보장 범위를 넘지 않는다. 본 조사로 데이터 유실이나 네트워크 결함을 확정한 것은 아니다.

### R7. 코멘트와 그림의 직접 연결 — P2, 설계 제안

**사용자 영향:** 같은 프레임에서 여러 명이 리뷰하면 어떤 그림이 어떤 지적의 근거인지 구분하기 어렵다. 해결된 피드백을 숨길 때 연관 그림의 처리도 명확하지 않다.

**근거:**

- `renderer/scripts/modules/comment-manager.js:221-251`: 코멘트는 시간·위치·본문·해결·답글·첨부 이미지를 저장한다.
- V3 그림은 `renderer/scripts/modules/review-data-manager.js:2436` 이후 별도 루트로 관리된다.

**수용 기준:** 재생 중 그리기 버튼을 누르는 순간의 동작 정책이 일관되고 UI에 드러난다. 기본 정지 정책을 선택하면 재생 정지와 continuous session/대기 중 advance 처리까지 함께 검증한다. 재생 유지 정책이면 입력이 고정되는 프레임·다음 컷 전환 시 작업의 처리 기준을 설명하고 검증한다. 실제 획 입력·전환 직전 입력의 저장 결과는 추가 네이티브 시험 대상으로 남긴다.

## 6. 하네스 자체 검토, 반례와 실제 발생 조건

초기 재현이 mock에 의해 만들어진 결과인지 검토하고, 보호되는 정상 경로를 추가로 실행했다. [review-self-audit.cjs](review-self-audit.cjs)의 결과는 [review-self-audit-result.log](review-self-audit-result.log)에 보존했다. 7개 대조 사례가 통과했고 종료 코드는 0이다. 제품 시험 1196개 합계와는 별도로 센다.

### 소스 사용의 충실도

- 공유 클릭 핸들러, 사이드바 제출 함수, 웹의 프레임 렌더 함수는 현재 파일의 시작·끝 앵커 사이를 그대로 추출한다. 함수 본문을 재작성하거나 반환값·조건문을 수정하지 않았다.
- CommentManager는 파일 전체에서 import/export 선언만 제거해 VM으로 실행한다. 클래스와 메서드 본문은 그대로다. logger와 인증 조회를 stub으로 공급했다.
- Windows 줄바꿈을 LF로 정규화하는 것 외에 추출 함수의 내용을 바꾸지 않았다. 자체 검토 결과 로그에 각 추출본의 SHA-256을 기록했다.
- UI 객체, 파일 존재 조회, 저장 결과, 클립보드, 캔버스 출력을 stub으로 대체했다. 실제 파일을 손상하거나 외부로 내용을 전송하지 않았다.

### 우선순위 재평가

- R1과 R3은 구체적인 실패 조건과 현행 함수 결과가 연결된다. 우선 수정 후보로 유지하되 실제 발생 빈도는 측정하지 않았다.
- R2는 앱의 댓글 모드 표시 결함과 웹의 핵심 전달 범위 제한을 묶었다. 유효 네이티브 문서·앱 모드 왕복은 §7에서 보강했다. 현재 배포 웹의 전체 영향은 별도 웹 조사 증거와 구분한다.
- R4는 P1 동작 불일치에서 P2 설계 개선으로 조정했다. 리뷰 대상 집합을 통일하자는 제안이며 데이터 손상 결함은 아니다.
- R5의 잘못된 안내 문구는 확정된 소스 불일치다. 미지원 키프레임 액션의 구현 필요성 자체는 사용 빈도와 대체 액션을 고려해 결정할 수 있다.
- R6과 R7은 미래 설계 제안이다. 이 조사 결과만으로 동기화 데이터 유실이나 코멘트·그림 데이터의 손상을 주장하지 않는다.
- R8은 보고서 담당자의 네이티브 관찰에 현재 소스와 기존 시험 의도를 대조한 후속 조사다. pause 부작용 금지를 기존 시험이 명시하므로 제품 동작 정책을 개선할 문제로 분류했다. 본 하위 조사에서 별도 네이티브 획 입력을 수행하지 않았다.
