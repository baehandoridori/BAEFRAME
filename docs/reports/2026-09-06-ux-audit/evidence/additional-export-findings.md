## AE01 이미지 붙여넣기 처리 중 이동하면 다른 영상·프레임에 추가될 수 있다

**권장 P1 · 코드와 현행 함수의 비동기 조건 재현 · 실제 앱 재현은 미실시**

### 사용자에게 생기는 일

영상 A의 특정 프레임에 참고 이미지를 붙여넣은 뒤 이미지 처리가 끝나기 전에 다음 영상 B로 넘어가면, 이미지가 B의 합성 레이어에 추가되고 성공 안내가 나온다. 같은 영상에서 프레임만 움직여도 처음 붙여넣은 위치가 아니라 처리가 끝난 시점에 추가된다.

파일을 바꾸는 경우는 리뷰 대상 자체가 달라지는 위험이다. 같은 영상에서의 시간 이동은 삽입 기준을 입력 시점과 처리 완료 시점 중 무엇으로 정할지 명확히 할 문제도 포함한다. 실제 잘못된 파일 저장까지 시험한 것은 아니다.

### 현행 코드의 근거

- `renderer/scripts/app.js:2988–3013`: 전역 `paste` 콜백은 이미지 압축·디코드인 `await getImageFromClipboard(e)` 전에는 영상이 열려 있는지 검사한다. 응답 후 원래 파일·문서·프레임이 여전히 유효한지 확인하지 않고 `addLayerFromDataUrl(image.base64)`를 호출한다.
- `renderer/scripts/modules/image-utils.js:191–200`: 클립보드 파일을 `compressImage(blob)`로 비동기 처리한다.
- `renderer/scripts/app.js:1415–1416`: 합성 레이어 관리자의 `getCurrentTime`과 `getBaseDuration`은 현재 `videoPlayer` 상태를 읽는다.
- `renderer/scripts/modules/composition-layer-manager.js:617–638`: `options.currentTime`이 없으면 추가 시점의 `this.getCurrentTime()`을 사용하고 현재 `this.layers`에 넣는다.
- 같은 파일 `570–583`의 `fromJSON()`은 새 리뷰의 합성 레이어 목록을 설치한다. 원래 영상에서 시작된 전역 붙여넣기 작업을 취소하거나 세대 번호로 구분하지 않는다.

결정적인 호출 순서는 다음과 같다.

```js
const image = await getImageFromClipboard(e);
const layer = await compositionLayerManager.addLayerFromDataUrl(image.base64);
```

### 재현 방법과 결과

현행 `app.js`에서 전역 `paste` 콜백을 그대로 추출했다. 현재 `CompositionLayerManager` 모듈을 import하고 실제 `addLayerFromDataUrl()`·`createCompositionLayer()`·`fromJSON()`·변경 통지 코드를 사용했다. DOM 렌더·시스템 클립보드 읽기·이미지 디코드 완료 시점은 모의 처리했다. 모든 영상명과 데이터는 합성 값이다.

이미지 디코드 Promise를 잠시 보류한 뒤 다음 세 경우를 비교했다. 시작은 모두 `synthetic/A.mp4`, 24fps, 1초(Frame 24)다.

| 대조 조건 | 이미지가 실제 추가된 manager의 대상 | 추가된 시작 시간·프레임 | 변경 통지·안내 |
|---|---|---|---|
| 이동 없이 디코드 완료 | A | 1초 / Frame 24 | `layerAdded`, 성공 안내 |
| 디코드 중 A에서 2초로 이동 | A | 2초 / Frame 48 | `layerAdded`, 성공 안내 |

성공 안내는 세 경우 모두 `클립보드 이미지를 합성 레이어로 추가했습니다.`였다. 대조군은 작업 대상이 바뀌지 않으면 기대한 Frame 24에 추가되는 것을 확인한다. 실제 OS 클립보드 지연 길이와 사용자에게 발생하는 빈도는 측정하지 않았다.

### 개선 방향과 수용 기준

입력 시점의 문서 정체·영상 세대·프레임을 기록한다. 이미지 처리가 끝났을 때 대상 문서가 바뀌었다면 새 문서에 조용히 추가하지 않고 취소·재시도 안내를 제공한다. 같은 문서에서 프레임이 이동한 경우에는 입력 시점에 붙이는 동작을 명시적으로 정하고 그 시간을 옵션으로 전달하는 방법을 검토한다.

수용 기준은 이미지 처리 중 A→B, A→B→A, 파일 닫기, 같은 파일 재열기, 프레임 이동에서 잘못된 대상에 레이어가 추가되지 않는 것이다. 변경 통지와 실제 리뷰 저장까지 연결한 후속 실기 검증이 필요하다.

기존 I06과의 차이: I06은 늦은 댓글 준비 응답이 재생 방식을 다시 전환하는 문제다. AE01은 클립보드 이미지라는 새 리뷰 자료가 **다른 문서의 현재 레이어 배열에 삽입되는 문제**다.

## AE02 투명 이미지를 붙여넣으면 투명도가 사라진다

**권장 P2 · 현행 압축 함수와 실제 캔버스 픽셀 변환으로 확인 · mpv 고유 문제는 아님**

### 사용자에게 생기는 일

투명 배경의 선화·포즈 가이드·부분 수정 참고 이미지를 영상 위에 붙이려 해도, 입력 과정에서 불투명 JPEG로 변환된다. 원래 비어 있어야 할 영역이 바탕 영상을 가리는 사각형이 된다. 그림을 덧대어 비교하는 리뷰 용도에서는 참고 이미지의 의미가 달라질 수 있다.

### 현행 코드의 근거

- `renderer/scripts/modules/image-utils.js:13–20`: 기본 압축 형식은 `image/jpeg`, 최대 1920×1080, 품질 0.85다.
- 같은 파일 `91–109`: `compressImage()`는 입력 형식과 관계없이 기본 설정을 합치고 캔버스의 `toDataURL(config.format, ...)`로 변환한다.
- 같은 파일 `191–200`: `getImageFromClipboard()`가 투명도 보존 옵션 없이 `compressImage(blob)`를 호출한다.
- `renderer/scripts/app.js:2998–3003`: 반환된 Base64를 합성 레이어로 사용한다.
- `renderer/scripts/modules/composition-layer-manager.js:624–637,481–501`: 반환된 이미지를 `sourceDataUrl`로 보관·직렬화한다. 합성 레이어가 나중에 원래 PNG의 투명도를 복원할 경로는 없다.

작은 원본도 이 경로를 우회하지 않는다. `loadImage()`의 Blob/File 분기는 디코드용 Object URL을 만드는 데만 쓰이고, `compressImage()`는 디코드 뒤 항상 새 캔버스와 `canvasToBase64()`를 거친다. 원본이 작다는 이유로 원본 PNG URL을 반환하거나 원본 MIME을 유지하는 조기 반환은 없다. 아래의 **4×4 PNG** 대조도 해상도 축소가 필요 없는 작은 입력이 기본 JPEG로 바뀐다는 사실을 확인한다.

### 픽셀 재현과 정상 대조

현재 `image-utils.js`의 설정·로드·리사이즈·Base64 변환·`compressImage()` 함수를 그대로 추출했다. 브라우저 캔버스 대신 저장소에 설치된 `canvas` 모듈의 실제 이미지 디코더·2D 캔버스를 사용했다. 투명한 4×4 PNG 중앙에 빨간 2×2 영역을 그려 합성 입력을 만들었다. 이미지는 메모리에서만 생성·변환했다.

| 조건 | 출력 MIME | 모서리 RGBA | 해석 |
|---|---|---|---|
| 입력 PNG | `image/png` | `[0, 0, 0, 0]` | 투명 |
| 현행 기본 `compressImage(input)` | `image/jpeg` | `[43, 0, 0, 255]` | 불투명으로 변환됨 |
| 같은 함수에 `{ format: 'image/png' }`를 전달한 대조 | `image/png` | `[0, 0, 0, 0]` | 투명 유지 |

JPEG 압축 때문에 불투명 영역의 정확한 RGB 색은 입력과 인코더에 따라 달라질 수 있다. 보고할 핵심은 특정 검정색으로 변한다는 단정이 아니라 **알파 값 0이 255로 바뀌는 것**이다. 실제 Electron 창에서의 픽셀 캡처는 하지 않았다.

### 개선 방향과 수용 기준

사진 첨부의 용량 최적화와 영상에 덧댈 합성 이미지를 구분한다. 합성 레이어용 붙여넣기에서는 알파가 있는 입력의 투명도를 보존하는 PNG 등 적절한 형식을 유지한다. 최대 해상도 제한을 유지할 경우에도 투명도 보존과 독립적으로 적용한다.

수용 기준은 투명 PNG, 불투명 사진, 고해상도 선화에서 입력·붙여넣기·저장·재열기 후 투명 영역과 이미지 비율이 일치하는 것이다. 이 재현은 PNG 옵션으로 투명도가 유지됨을 확인했을 뿐, 그 옵션을 제품에 적용한 수정은 아니다.
